# シッテムの箱 議事録設計

## 1. 目的と状態

「シッテムの箱 議事録」は、private Discord Guildで正常に完了した討論を、
認証済みmemberが後から閲覧するWeb applicationである。

本書は実装中機能の正本であり、現行1.0 Botの実装済み契約を変更しない。
実装状態、検証証拠、release状態は[[20_実装・試験・検証記録]]へ記録する。

### 実装状態

- Records repository／contract／CI境界とsource Stream／専用OIDC roleは実装済み。
- Archive／Statistics／Session Tableを所有するRecordsStatefulと、Projector／Backfill Lambdaを所有する
  RecordsApplicationはdeploy済みである。各Lambdaは`Active / Successful`で、Projector DLQは0である。
- M2のBackfill dry-runとapplyは52候補すべてで`complete=true`となり、52件のArchiveを投影済みである。
- OAuth／Session／Read API／requester avatar cacheはM3としてProduction Releaseまで完了した。
- SPA／Edge、一覧／詳細はM4としてProduction Releaseとbrowser受入まで完了した。
  期間未指定Query、avatar origin、responsive detail、投票graphの受入指摘は解消済みである。
- M5-Aの勝利回数／依頼回数rankingはProduction Releaseとbrowser受入まで完了した。
- M5-Bの概算費用はProduction Releaseと初回集計まで完了した。
- runtime prompt互換層とADMINの認可、read-only status、Web UIはProduction Releaseとbrowser受入まで完了した。
  prompt editor、immutable revision、履歴、rollbackはsoftware実装済みで、Records Production Releaseと
  初回active revision作成は未実施である。
- 親愛度のArchive v2、profile projection、3人格別ranking、詳細API／Web表示はsoftware実装対象である。
  Records Production Releaseを先行し、source schema v8と質問評価を含むCore Production Releaseを後続させる。

### 対象

- 完了した討論の一覧と詳細。
- 3人の初回意見と最終案。
- 投票者、投票先、投票理由。
- Pythonが決めてDynamoDBへ保存したwinner、勝利の言葉、最終決定。
- 勝利回数、依頼回数、Fargate／Lambda／OpenAI／その他AWSの円換算概算費用。
- 議論ごとの3人格の親愛度変化と、質問者ごとの3人格別親愛度ランキング。
- Discord OAuth2で確認した対象Guild memberだけの閲覧。
- 認証済み利用者へ共通に見せる`SYSTEM ACCESS`導線とread-only status閲覧・明示更新。
- 認証済み利用者が参照できる5種類のruntime promptと履歴比較、管理者だけが実行できる更新・rollback。

### 対象外

- realtime進行表示、WebSocket、AppSync Events。
- 討論を順番に再生する長時間animation。
- Web側でのwinner再計算、LLM再生成。
- Evidence、source URL、議論所要時間の表示。
- Bootstrap、Bootstrap風管理画面、汎用SaaS template。
- ADMINからのdeploy、task停止、DLQ削除、Lambda invoke、runtimeの強制停止。

## 2. Architecture

```text
既存DebateTable
  -> DynamoDB Stream
  -> Archive / Affection Projector Lambda
  -> Records Archive / Statistics / Media

Browser
  -> CloudFront
    -> private S3 SPA
    -> API Gateway HTTP API
      -> Auth / Read API Lambda
      -> Session / Archive / Statistics

Runtime task
  -> active runtime prompt revision（SSM）

Browser ADMIN
  -> Admin Status Lambda
  -> read-only AWS status
  -> Admin Config Lambda
    -> immutable runtime prompt revision（SSM）
    -> content-free audit（Statistics Table）
```

- Projectorは`COMPLETED`候補を受け、source partitionをstrongly consistentに読み直す。
- Affection Projectorはsourceの質問者profile変更をstrongly consistentに読み直し、既存identity HMACで
  opaque requester keyへ変換してStatisticsへ投影する。private Discord IDはRecords側へ保存しない。
- FAILED／CANCELLEDはRecords Archiveへ作成しない。
- 保存済みwinnerを既存Python `select_winner()`で再検証する。
- Stream重複はprojection markerとsource fingerprintでno-opへ収束させる。
- Projector／BackfillのArchive書込みは`dynamodb:PutItem`を
  `dynamodb:EnclosingOperation=TransactWriteItems`へ限定し、standalone writeを許可しない。
- Stream partial failureはDynamoDB `SequenceNumber`を返す。失敗logはerror codeと
  cancellation reason codeだけを記録し、message、key、本文、identifierを含めない。
- Runtime、Records service、Web、CDK、release artifactを分離する。
- Records-only変更はproduction Fargate imageをbuildしない。

## 4. Source boundary

source DebateTableのcurrent schemaはv8とし、v7 recordはmemory上で互換読込する。PK、SK、GSIは変更しない。
Stateful Stackへ`NEW_IMAGE` DynamoDB Streamだけを追加する。

ProjectorはStream eventを公開可能性の証拠には使わない。既存repositoryで全partitionを読み、
次をすべて満たす場合だけ投影する。

- current attemptとDebateがCOMPLETED。
- 初回意見、最終案、投票が各3件。
- final decisionとterminal deliveryが確定。
- 新規議論は親愛度評価が`applied`または`unavailable`として確定している。既存v7議論は遡及評価しない。
- 既存domain validationを通る。
- `select_winner()`と保存済みwinnerが一致する。

Evidence、Discord message／interaction ID、delivery／fencing metadata、provider response IDは
Archiveへ複製しない。

## 5. Records data model

### Archive Table schema v1／v2

`PK=RECORD#<record-id>`のpartitionへ次を保存する。

| SK | 内容 |
|---|---|
| `META` | 完了日時、質問、依頼者表示、参加者snapshot、winner、票数、tie-break有無。v2は3人格の変更前、質問評価、実増減、変更後も保持 |
| `INITIAL#<slot>` | 初回意見 |
| `FINAL#<slot>` | 最終案 |
| `VOTE#<voter>` | 投票先と理由 |
| `DECISION` | winner、勝利の言葉、最終決定、実行案、注意点 |
| `PROJECTION#V1`／`PROJECTION#V2` | Archive schemaに対応するsource fingerprintとprojection metadata |

GSIは完了日時、winner、内部requester keyの3経路とする。
requester keyはproduction secretでDiscord user IDをHMAC化し、生IDをArchiveやAPIへ出さない。

親愛度を持つsource schema v8の新規議論はArchive v2へ投影し、評価不能時も`unavailable`を記録する。
既存のArchive v1は12 itemと従来fingerprintを維持して読込可能とし、詳細APIでは親愛度を`null`とする。
v2も同じ12 item構成を維持し、親愛度は`META`へ含める。v1をv2へ遡及変換しない。

同じfingerprintはno-op、異なるfingerprintは`PROJECTION_CONFLICT`とし、自動上書きしない。
1討論分は1 transactionで書き、action数、各item 400 KB、aggregate 4 MBを事前検証する。

### Statistics Table

- `RANKING#WINS / CURRENT`
- `RANKING#REQUESTS / CURRENT`
- `AFFECTION#PROFILE / <opaque-requester-key>`
- `RANKING#AFFECTION / CURRENT`
- `RANKING#AFFECTION#GEN#<generation> / META|PAGE#<index>`
- `RANKING#AFFECTION#CATALOG / <generation>`
- `AFFECTION#SEED / CURRENT`
- `COST#DAILY / <date>#FARGATE|LAMBDA|OPENAI|OTHER_AWS`
- `FX#DAILY / <date>#USDJPY`
- BackfillとAWS／OpenAI／Frankfurter collectorのcheckpoint

Cost collector checkpointは`next_date`、初回取込完了状態、最終成功時刻を保持し、provider失敗時は
進捗を変えずにcontent-freeな最終failure code／時刻だけを記録する。次のschedule成功時はfailure
metadataを消し、正常なcheckpointへ置換する。

ランキングは15分ごとにArchive GSI1の全pageから再計算する。friend-scaleを前提として、
複雑なincrement counterとduplicate補正は導入しない。勝利rankingは3 participant全員、
依頼rankingはinternal requester key単位の上位10人を保持し、同数は競技順位の`1, 1, 3`とする。
同数内はdisplay nameとinternal keyの順で安定化する。winsとrequestsの2 snapshotは
同一DynamoDB transactionで更新し、Archiveの未知schema、不正winner、duplicate METAでは旧snapshotを維持する。
APIはcurrent requester profileを優先し、internal requester keyをresponseへ含めない。

親愛度profileは3人格の現在値を`0〜1000`で保持する。source profileから投影した行は単調増加する
source versionで収束させ、Stream重複や順序逆転で古い値へ戻さない。既存Archiveに登場し、実profileが
まだない質問者だけをRanking Lambdaが500点で条件付きseedする。実profileはseedで上書きしない。
15分集計は3人格それぞれについて全profileをscore降順、表示名、opaque keyの順で安定sortし、同点を
競技順位`1, 1, 3`とする。親愛度rankingはcontent-free catalogを先に作り、50人単位のimmutable pageと
generation metadataを完全保存した後、勝利、依頼、seed checkpoint、active generation pointerを
CAS付きtransactionで切り替える。途中失敗、
欠落、不正profile、3人格間の質問者集合不一致では旧pointerを維持する。旧generationはcursor期限1時間に
15分の猶予を加えた75分間保持し、期限後にpage／metadata、catalogの順でbest-effort削除する。削除失敗時は
catalogを残し、次回集計で収束させる。page保存途中で失敗した未公開generationもcatalogから同じ手順で回収する。

### Session Table

- OAuth stateは10分、Sessionは90日で`expiresAt`によるTTL削除を行う。TTL削除の遅延を
  認可へ使わず、handlerも`expiresAt`を検証する。
- requester profileは`expiresAt`を持たず、本人がOAuth loginするたびに表示名とavatar参照を更新して
  無期限に保存する。旧30日profileは次回login時に無期限recordへ置き換える。
- state、browser nonce、session、CSRF tokenはdomain-separated HMACだけを保存する。
- OAuth access／refresh tokenはGuild確認後に破棄する。

## 6. Authentication and privacy

- 既存Moderator ApplicationのOAuth2 Authorization Code flowを利用する。
- scopeは`identify`と`guilds.members.read`。
- callbackで設定済みGuildのcurrent user memberを確認する。
- OAuth stateはstrong readと条件付きclaimで一度だけ使用する。token exchange、current user、Guild memberの
  provider callに失敗した場合はSessionを作成しない。
- OAuth nonceとSession cookieはSecure、HttpOnly、SameSite=Lax、Path=/、Domainなしの`__Host-` cookieとする。
  CSRF tokenは認証済みSession responseだけで返し、DynamoDBのHMACとconstant-time比較する。
- POST logoutはOriginとCSRF tokenを検証する。
- API responseは`Cache-Control: private, no-store`。

browserへDiscord client secret、OpenAI Admin key、AWS credential、raw requester ID、
internal DynamoDB keyを渡さない。

### ADMIN authorization

- sidebarとmobile navigationの`ADMIN`導線は、認証済み利用者全員へ表示する。これは発見可能性のためであり、
  権限の根拠ではない。
- 管理者はprivate production inputに登録したただ1つのDiscord user IDからidentity HMACで導出した
  requester keyと、Sessionのopaque requester keyをconstant-time比較して判定する。username、display name、
  avatar、role名は認可に使用しない。
- 全status／prompt APIはserver-sideで有効なSessionを毎回確認し、未認証は401とする。status取得・明示更新と
  promptの現行本文・履歴・revision本文参照は、認証済み利用者全員へ許可する。
- Session responseの`isAdmin`はprompt write操作のUI表示用だけとする。promptの反映・rollbackではserver-sideで
  requester keyを毎回再判定し、認証済み非管理者は403とする。

## 7. Avatar

- participant画像は3体のDiscord Botのcurrent user avatarを正とし、専用operator tool
  `tools/sync_records_participant_avatars.py`でprivate media bucketへ同期する。Records Lambda、browser、
  ArchiveへBot tokenを渡さない。
- participantごとの保存先は`participants/<slot>/avatar.webp`の固定keyとする。Read APIは全recordで
  このcurrent-profile keyを解決し、議論完了時点のavatar keyや画像をArchiveへ保存しない。
- operator toolは3体のBot identityと256 px WebPをすべて取得・検証してから、対話確認後に固定keyを
  上書きする。RIFF構造検査に加えてlocal ImageMagickの`magick`で実デコードし、256×256を確認する。
  上書き前の全VersionIdを記録し、失敗時はSDK retryが作成したものを含む全新規versionを列挙・削除して
  再照合する。slotごとのrollback結果だけをcontent-freeに報告する。
  `--check`はtoken本文を復号せずSSM metadataとMedia bucket到達性だけを確認する。
- participant avatarが未同期、または画像取得に失敗した場合はslot別の幾何学placeholderを使う。
- requester画像は本人のOAuth login時にcacheする。
- Guild avatarをuser avatarより優先し、128 px WebPかつ512 KiB以下だけをprivate media bucketの
  opaqueな`requesters/` keyへ保存する。失敗時もloginを継続する。
- 未login requesterは円形placeholderを使う。login済みrequesterのprofileとavatar参照は無期限に保持する。
- APIが有効なasset keyへ発行するpresigned GET URLは5分とし、bucket名やobject keyをresponse fieldへ出さない。
- presigned URLはCloudFront CSPが許可する同regionのS3 virtual-host endpointで生成する。
- source schemaとArchive schemaへ歴史的avatar snapshotは追加しない。旧Archive itemに
  `avatar_asset_key`が存在してもRead APIは無視する。

| endpoint | 用途 | 状態 |
|---|---|---|
| `GET /api/v1/auth/discord/start` | OAuth開始 | 実装済み |
| `GET /api/v1/auth/discord/callback` | Guild確認とSession作成 | 実装済み |
| `GET /api/v1/session` | anonymousを含むSession確認 | 実装済み |
| `POST /api/v1/logout` | Origin／CSRF検証後のSession削除 | 実装済み |
| `GET /api/v1/records` | 完了議論一覧 | 実装済み |
| `GET /api/v1/records/{recordId}` | 議論詳細 | 実装済み |
| `GET /api/v1/insights/rankings` | 勝利／依頼ランキング | 実装／Release／受入済み |
| `GET /api/v1/insights/affection-rankings` | 3人格別の全質問者親愛度ランキング | software実装、Release待ち |
| `GET /api/v1/insights/costs` | 期間別のJPY概算費用 | 実装／Release／受入済み |
| `GET /api/v1/admin/status` | cached read-only service status | 実装／Release／受入済み |
| `POST /api/v1/admin/status/refresh` | status cacheの明示更新 | 実装／Release／受入済み |
| `GET /api/v1/admin/prompts` | 現行またはlegacyの5本文 | software実装、Release待ち |
| `POST /api/v1/admin/prompts/apply` | 新revision作成と有効化 | software実装、Release待ち |
| `GET /api/v1/admin/prompts/revisions` | content-free履歴 | software実装、Release待ち |
| `GET /api/v1/admin/prompts/revisions/{revision}` | 選択revision本文 | software実装、Release待ち |
| `POST /api/v1/admin/prompts/rollback` | 選択内容から新revision作成 | software実装、Release待ち |

一覧はGSI1／winner指定時GSI2を使い、1 pageはdefault 12、maximum 50とする。期間filterは設けず、
`sort=newest|oldest`で全Archiveの昇順／降順を選択し、defaultは`newest`とする。cursorはindex、
winner、sort、limit、1時間の期限、LastEvaluatedKeyをSession keyでHMAC署名する。詳細は43文字の
opaque record IDだけを受理し、base tableをstrongly consistentに全page取得してArchive v1／v2の12 itemを
exactに再構成する。詳細responseはschema v2へ統一し、Archive v1では`affection=null`、v2では3人格の
変更前、質問評価、実増減、変更後を返す。欠落、重複、未知record type、winner不一致は公開せず503とする。

投票score、Evidence、source fingerprint、requester key、attempt ID、所要時間は返さない。
Read APIは保存済みwinner、勝利の言葉、最終決定を表示し、winnerを再計算しない。
親愛度ランキングはdefault／maximum 50人ずつ返し、`limit`と署名付きopaque cursorで全質問者を取得できる。
cursorはgeneration、offset、limit、1時間の期限をSession keyでHMAC署名し、改ざん、期限切れ、limit不一致を
`CURSOR_INVALID`として拒否する。初回cursorの期限を後続pageへ固定継承し、取得のたびに延長しない。
3人格は常に同じglobal offset範囲と全体順位を返す。2 page目以降は直前pageも検証専用に読み、
page境界をまたぐ同点の競技順位と質問者の重複を検証してからrequested rangeだけを返す。private identifier、
internal key、質問ごとの評価理由、履歴は返さない。pointer、generation metadata、pageの世代、件数、
participant集合が一致しない場合は503とし、部分的な順位を公開しない。

Python Pydantic modelをcontract正本とし、OpenAPI／JSON Schemaをdeterministic生成する。
CIは再生成結果とrepository artifactをbyte比較する。TypeScriptは生成contractを参照し、
winnerやdomain ruleを再実装しない。

promptの反映・rollbackは有効なSession、server-side管理者再判定、exact Origin、CSRF token、16〜128文字の
idempotency keyを必須とする。status明示更新も有効なSession、exact Origin、CSRF token、idempotency keyを
必須とするが、管理者再判定は要求しない。prompt JSONは64 KiB以下、unknown field／base64／余分・重複queryを拒否する。
全JSON responseは`private, no-store`であり、SSM parameter名、raw identifier、AWS resource identifierを
error、access log、telemetryへ含めない。

## 9. UI/UX

日本語の正式製品名は「シッテムの箱 議事録」とする。Webのlogin／sidebar／OGPで使う
英字brand lockupは`THE SHITTIM`／`CHEST ARCHIVE`の2行へ固定する。

- LINE Seed JPは公式LINE release `v20251119`のOFLとchecksumを固定し、Regular／Bold／ExtraBoldの
  versioned WOFF2をself-hostする。
- 英字brand lockupと`AUTHENTICATE`／`LOGOFF`にはDelogyを使い、`lang="en"`を指定する。
  loginでは320px幅でも各行の途中で改行せず、sidebarでは既定幅へ収める。
- card／detailの完了日時はsourceのISO 8601値を保持したまま、固定JSTの
  `YYYY年M月D日 HH:mm`形式で表示する。
- 日本語本文は`lang="ja"`、`line-break: strict`、`word-break: auto-phrase`、
  `text-autospace: normal`を使い、未対応browserでは通常改行へfallbackする。見出しには
  `text-wrap: balance`、段落には`text-wrap: pretty`、単独の長文には最大`48ic`を使用する。
- browser標準の日本語組版を正とし、BudouX等による本文のJavaScript分割、`text-align: justify`、
  proportional-width指定は使用しない。
- light themeは透き通った水色、白、淡いcyan、薄いpinkをbaseにする。dark themeは「夜の記録庫」を
  themeとし、純黒ではなく深い紺色、低彩度のcyan／pinkの光、薄いgridを使う。darkでも
  participantのcyan／pink／lavenderとwinnerのgoldを維持し、本文はWCAG AA 4.5:1以上、
  control／focus／境界は3:1以上を満たす。
- rings、grid、triangle等はCSS／SVGで独自実装する。
- 参考作品のlogo、画面、assetを複製しない。
- participant／requester avatarはDiscordを踏襲した円形表示とする。
- 一覧の絞り込みは読み込み済みcardの質問／winner検索、読み込み済みcardから作る依頼者の
  完全一致プルダウン、winner、並び順だけとし、開始日／終了日は表示しない。
- 一覧cardは全体を1つのnative linkとし、見出しと下部導線に別々のlinkを置かない。
  下部の「記録を読む」は視覚的な手掛かりとして維持し、keyboardと別tab表示をnative linkで保証する。
- 一覧cardの空き領域には、orbit、triad、constellation、reticle、prism、wave、lattice、compass、
  horizon、helix、vector、portalの12種類を抽象化した低opacityの幾何学装飾を置く。
  record IDをseedにした安定疑似乱数から、基本形、5種類の背景frame、4色のaccent、位置、角度、
  縮尺、左右反転、opacityを独立して選び、同じ基本形でも構図が単調にならないようにする。
  同じrecordは再描画や並び替え後も同じ装飾を維持し、真の乱数によるちらつきを発生させない。
  装飾はcard内へclipし、`aria-hidden`かつpointer操作の対象外とし、本文より前面へ出さない。
- 並び順は新旧の2状態を`NEW / OLD`で常時表示するnative radio segmentとし、初期値は`NEW`
  とする。選択pillはCSS `transform`だけで200msで移動させ、reduced motionでは即時切替にする。
- login成功後は`WELCOME, SENSEI.`、logout成功後は`GOODBYE, SENSEI.`を使い、
  それぞれ約2秒の全画面brand transitionを表示する。logout時はtransition完了後に保護対象の

| Stack | resource |

| `RecordsStateful` | Archive／Statistics／Session Table、media bucket、DLQ |

## 11. CI and Release

- `records-ci.yml`はRecords変更を分類し、Python、contract、Web、CDK、securityを検証する。
- required `records-gate`は非対象PRでも明示的N/A成功とする。
- current CIのrequired `container-arm64`と`grype`名は維持する。
- Docker context／container risk入力が変わらないRecords-only変更ではheavy buildをskipする。
- Records ReleaseはGitHub OIDC、fixed main SHA、artifact attestation、Change Set、
  `production` Environment承認を使う。
- Auth／ReadをPython 3.14 ARM64 Lambdaとして分離し、それぞpublished versionと`live` aliasを
  HTTP API payload v2.0へ接続する。M5-B時点のAPIは8 routeを持ち、access logはrequest ID、route、status、
  latency、response sizeだけを90日保持する。ADMIN Release後はStatusにも独立した`live` aliasを置き、
  APIは10 routeとなる。
- Lambda bundleのbase64 SHA-256はdefaultなしCloudFormation parameter、Change Set、attested manifest、
  Lambda Versionで閉包し、planとdeployの両方で照合する。
- Records ReleaseはCDK CLIを経由せずChange Setを直接実行するため、各Stackの実行または正常な
  no-opを確認した直後にtermination protectionを明示的に有効化し、再読して`true`を検証してから
  次Stackへ進む。CDK Stack metadataだけをlive protectionの根拠にしない。
- no-op Stackではplanが受理する`CREATE_COMPLETE`、`UPDATE_COMPLETE`、
  `UPDATE_ROLLBACK_COMPLETE`、`IMPORT_COMPLETE`を同じstable statusとしてdeployでも受理する。
- `ROLLBACK_COMPLETE`はplanが受理しない。初回作成失敗後のRecordsApplicationを再Releaseする前に、
  rollback shell削除を独立承認し、Stack不存在、対象空LogGroup不存在、active Change Set 0、
  deployment lock openを確認する。Release workflowはrollback shellを暗黙に削除・復旧しない。
- Change Setの`CREATE`／`UPDATE`は作成前のStack状態から決定してattested manifestへ保存し、
  deployはmanifestの区分だけを使う。`DescribeChangeSet`から区分を推測しない。
- `CREATE_COMPLETE / AVAILABLE`だけを実行し、`FAILED / UNAVAILABLE`かつno changesの
  Change Setは正常なno-opとしてmanifestへ記録したうえで、承認待ち前に削除する。
- Records ReleaseはECR pushとFargate image buildを行わない。
- M3 post-deploy smokeは`GET /api/v1/session`のanonymous 200／no-store／Set-Cookieなしと、
  未認証`GET /api/v1/records`の401だけを実行する。OAuth startはstate writeを伴うため自動実行しない。
- M5-AはRecordsApplicationにreserved concurrency 1のRanking Lambdaと15分scheduleを追加し、
  Read LambdaにStatisticsの勝利／依頼snapshotを原子的に読む`TransactGetItems`と
  `GET /api/v1/insights/rankings`を追加する。親愛度追加後は同じscheduleでArchive由来の500点seed、
  3人格の全profile rankingをimmutable page generationへ保存し、完全保存後にseed checkpointとactive
  pointerを勝利／依頼snapshotと同一transactionで切り替える。Read Lambdaはactive generationのmetadataと
  必要なpageだけをstrong readし、`GET /api/v1/insights/affection-rankings`へ返す。
  RecordsStatefulはno-opとし、Discord RuntimeやFargate imageを変更しない。
- M5-BはRecordsApplicationにreserved concurrency 1、timeout 300秒のCost Lambdaを追加する。
  AWS／Frankfurterは毎日03:17 UTC（12:17 JST）、OpenAIは毎時37分に同じLambdaへ別modeで配送し、
  asynchronous retryは0とする。Read LambdaはStatisticsのCost／FX partitionをstrongly consistentに読み、
  `GET /api/v1/insights/costs`で認証済み利用者へJPY換算結果だけを返す。
- M4ではRecords Release manifest schema v3がTokyoのStateful／Applicationとus-east-1のEdge Change Set、
  Lambda bundle hash、deterministic Web ZIP hashを同じfixed main SHAへ結合する。
- Edgeはprivate versioned S3、OAC、CloudFront、us-east-1 ACM、Route53 A／AAAAを所有する。
  public certificateはECDSA P-256（`EC_prime256v1`）、viewer security policyはTLS 1.3だけを許可する
  `TLSv1.3_2025`とする。
  RSA 2048からECDSA P-256への一回限りの証明書replacementは、同じdomain／validation／tagを維持し、
  `KeyAlgorithm`だけが変わるChange Setに限定して許可する。
  `/api/*`はcacheせずcookieをAPI Gatewayへforwardし、`/assets/*`だけimmutable cacheを使う。
- Web artifactはattestationとhash、pinned SyftのSBOM hashをdeploy直前に再検証し、hashed assetを
  先にuploadして`index.html`を最後に更新し、`/index.html`だけをinvalidationする。過去hash assetは
  即削除しない。公開後のsmoke失敗では直前のversioned `index.html`を復元して再invalidationする。
- rollbackはLambda alias、S3 object version、CloudFront invalidationで行い、Archiveを削除しない。
- 親愛度の配信はRecords Production Releaseを先に行い、Archive v2／Projector／Ranking／Read API／Webが
  source v8を受理できることを確認してからCore Production ReleaseでFargate imageとsource schema v8を配信する。
  Coreがprofileを書き始めた後は親愛度recordを削除するrollbackを行わず、forward fixする。

### ADMIN runtime／status delivery

- Runtime側の互換層を先行Releaseし、active pointerが未登録なら既存のversioned persona設定を使う。
  active pointerが存在するのにrevision、manifest、checksum、5 promptのいずれかが欠落または不正なら、
  runtime taskはfail closedとする。
- Records側の最初のADMIN Releaseより前にReleaseIdentity Stackだけを先行更新し、Records plan roleが
  exact Runtime Stackのparameter metadataを参照できることを確認する。通常のRecords Releaseは
  ReleaseIdentityを更新しないため、この先行工程を省略しない。
- Runtime taskは開始時に1 revisionだけを読み、task中のhot reloadはしない。稼働中taskを停止せず、
  Scale-to-Zero後の次taskから反映する。task開始時にはcontent-freeな読み込みrevisionだけをdurable control stateへ
  記録する。
- Admin Config LambdaはPython 3.14／ARM64、512 MiB、timeout 15秒、reserved concurrency 2とし、Statusとは
  function、role、aliasを分離する。管理対象はsystem、moderator、participant 3 slotの5本文だけで、LF／NFCへ
  正規化し、各3,500 UTF-8 bytes以下を要求する。winner、schema、tool、Evidence、`store=false`はcode所有とする。
- revision IDは`r`と26文字の小文字Crockford ULIDとする。5本文とmanifestをStandard SecureStringへ
  `Overwrite=false`で保存して再読込し、全checksum一致後にだけcontent-freeなactive Stringを更新する。
  manifestはschema、revision、UTC作成日時、publish／rollback、base revision、本文別SHA-256を持つ。
  同一内容、base競合、idempotency key再利用を409で拒否し、pointer更新後のaudit失敗は次回読込で回復する。
- Statistics Tableの`ADMIN#PROMPT`には`CURRENT`、`REVISION#<revision>`、hashed idempotency recordだけを保存し、
  本文や差分を置かない。rollbackは選択revisionから新revisionを作り、既存revisionを上書きしない。
  revisionは使用中を含む最新5世代（使用中1＋過去4）だけを保持する。新revisionの完全保存、再検証、active切替、
  audit完了後に限り、6世代目以降の非active revisionについてSSMの5本文とmanifestを先に削除し、続いて
  content-free summaryを削除する。途中失敗は次回read／writeで同じ対象を再処理し、active revisionは削除しない。
- Records ReleaseはRuntime Stackの`vNNNN` config versionを検証してConfig Lambdaへ名前とversionだけを渡す。
  Releaseはactive revisionを作成せず、初回は管理者がRelease後にlegacy内容を管理版として登録する。
- Admin Status Lambdaは第1段階のECS、ECR、Inspector、S3、DynamoDB、Lambda、CloudFront、SQS、
  API Gateway、EventBridge／Scheduler、CloudFormation、SNSと、第2段階のSSM設定準備、
  Budgets／Cost Anomaly、Signer、外部費用collector鮮度をallowlistする。AWS／CloudWatchのread-only APIと
  Statistics Tableの`COLLECTOR#COST` checkpoint metadataおよび`ADMIN#INSPECTOR_TRANSLATION`の
  日本語概要cacheだけを使い、resultはprocess-localで最大60秒cacheし、明示更新時だけ期限後に再取得する。
  message本文、resource ID／ARN／bucket名／queue URL、Discord情報は取得・responseへ含めない。
- Admin Status Lambdaはtimeout 30秒、reserved concurrency 2とする。Webはprompt本文／履歴の並行GETと
  status取得を許容し、Admin GETが429／503となった場合だけ250〜500 msのjitter後に1回再試行する。
  POSTは自動再試行せず、Status取得中は手動更新を無効化して同一画面内の競合を防ぐ。
- statusはdesired=0／running=0／pending=0をScale-to-Zeroの`IDLE`として正常に表示する。overall alarm数、
  runtime heartbeat／active debate／outbox／prompt revision、ECRのタグ付きimage一覧とInspector scan、
  table protection／stream／TTL、Lambdaの
  直近集計、CloudFront TLS／certificate期限、Projector DLQの件数とage、HTTP APIの4xx／5xx／latency、
  schedule失敗、Stack状態／last recorded drift、SNS配信、SecureStringの存在数、予算消化率、署名profile、
  AWS／OpenAI／Frankfurter最終成功時刻など、運用判断に必要な集約値だけを返す。SSM値、予算金額、
  通知先、checkpoint cursor、OpenAI project ID、外部API response本文は返さない。
- 発生中のCloudWatch composite alarmは件数に加え、allowlist済みのunderlying metric alarm codeだけを
  severityとservice labelへ変換して返す。画面では日本語の原因名と対象service cardへのanchorを表示し、
  AlarmDescription、ARN、resource ID、未知のalarm名を公開しない。
- ECRは現存するタグ付きimageを登録日時順に並べ、tag、media type、size、push日時、最終pull記録を返す。
  固定の「本番版」用途名は付けず、digest、repository名、ARN、account IDはresponseへ含めない。
- Inspectorはタグ付きimage単位で表示する。Critical／High／Medium／全件は
  `ListFindingAggregations`を正とし、同APIが独立countを返さないLow／Untriagedだけを、全page取得したactive findingから
  補助集計してaggregate totalとの整合を検証する。Critical／Highはvulnerability ID、100〜300文字の日本語概要、
  影響package、検出version、修正版候補、package manager、修正可否だけを返す。
  finding ARN、image digest、raw英語description、resource IDはstatus収集結果へ残さない。
- Inspector概要翻訳はreserved concurrency 1、timeout 5分の専用Lambdaを毎時7分に起動し、現存するタグ付きimageの
  active Critical／Highから未翻訳descriptionを最大50件選び、10件ずつ`gpt-5.6-luna`へ渡す。
  descriptionはuntrusted dataとして扱い、Responses APIのStructured Output、reasoning effort `none`、`store=false`、
  toolなしで100〜300文字の平易な日本語へ変換する。CVE IDと正規化descriptionからcontent hashを作り、
  Statistics Tableの`ADMIN#INSPECTOR_TRANSLATION`へsource hash、日本語概要、model、翻訳時刻だけを保存する。
  Admin Statusは現存対象のcache件数、未翻訳件数、cache内の最終翻訳日時を返し、DynamoDB cardへ表示する。
  cache読取不能時は3項目を未取得とし、0件として扱わない。raw description、OpenAI API key、finding ARNは
  保存・log出力・公開しない。未翻訳は推測せず翻訳準備中とする。

## 12. Cost

- 公開通貨はJPYだけとし、providerのUSD原価とFrankfurter v2の日次`USD/JPY`参照rateは
  Statistics内部台帳にだけ保持する。金額とrateはPython `Decimal`で計算し、6桁へ
  `ROUND_HALF_EVEN`した4内訳の和を公開totalとする。wire値は監査用に6桁を維持し、Webの金額表示だけを
  decimal stringから1円単位へ切り上げて整数化する。stacked barの比率以外をJavaScript `Number`で再計算しない。
- AWS Cost ExplorerはProject tag、日次`UnblendedCost`、Service／Usage Typeで全pageを取得する。
  Fargate usageをFargate、AWS LambdaをLambda、残余のProject帰属費用をその他AWSへ分類し、
  Credit／Refundと共有固定費のAmazon Route 53を除外する。その他AWSの内部componentには
  CloudWatch、Public IPv4、DynamoDB、S3、CloudFront、API Gateway、ECR、Inspector、未知serviceの
  residualを保持する。
- OpenAI Organization CostsはAdmin keyとexact project IDで日次bucketを全page取得し、project、USD、
  bucket境界、非負amountを検証する。Admin keyとproject IDはCost Lambdaだけがexactな2 SecureStringから
  読み、Auth／Read／browserへ渡さない。
- FrankfurterはCollectorだけが固定originのv2 `/rates`へredirectなしで接続する。USD／JPY、日付、正数rate、
  重複／欠落を検証する。確定済みの過去日にrate欠落があれば失敗とし、別日のrateで補完しない。
  日本時間の進行中当日だけは、日次rateがまだ公開されていない末尾欠落を許容する。同日rateの公開までは
  保存済みの直前日rateで当日分だけを暫定換算し、responseを`partial`に保つ。翌日以降の7日再取得で
  同日rateへ置き換える。rate取得失敗時もUSD原価は保持する。
- 初回は日本時間の当日を含む180日を30日window 6回で収集し、checkpointごとに再開可能にする。
  完了後は直近7日を再取得する。AWS／FrankfurterとOpenAIは独立して正常値を保存し、一方の失敗で
  他方の値を削除しない。日次recordは無期限に保持する。
- APIの期間とtimestampは`Asia/Tokyo`へ統一する。providerの監査可能な日次bucket自体は変更せず、
  時間別dataを推測配賦して厳密なJST日次額を生成しない。current day、AWS estimated、source／rate欠落は
  `partial`、有効な換算値がない場合は`unavailable`とする。
- network、429、5xxだけを`Retry-After`上限付きで1回再試行し、認証、422、schema不正は再試行しない。
  logはmode、件数、安定したfailure codeだけとし、cursor、project ID、金額、secretを含めない。
  HTTP clientのrequest URLを含むINFO logも抑止し、query string経由でproject IDを残さない。

## 13. Backfill

source tableにstatus GSIがないため、manual Backfill Lambdaが`debate_meta`を低速Scanする。

- dry-runを先に実行し、外部へは累積件数と完了状態だけを出す。
- dry-run／applyの両方でcandidate partitionをstrongly consistent Queryし、同じpure projectionで
  source schema、完了状態、terminal delivery、winner、公開item形状を再検証する。
- Lambda 1 invocationはsource itemを最大100件評価し、candidateはその内数とする。15分以内に
  終了する。
- 承認済みBackfill workflow 1 runは同じmodeとpage limitでLambdaを最大25回だけ順次Invokeし、
  checkpointから`complete=true`へ到達した場合だけ成功する。25 pageで未完了の場合はfail closedとし、
  保存済みcheckpointから新しいrunで再開する。workflowと一時credentialは最大60分に制限し、
  最終累積件数だけをsummaryへ記録する。
- dry-runはArchive writeを0件に保つ一方、Statistics Tableのdry-run専用checkpointへ内部cursorと
  累積件数を保存する。再dispatchは次pageから再開し、完了後はterminal no-opとする。
- applyは独立したapply専用checkpointにより必ず先頭から開始し、Projectorと同じpure projectionを
  使用する。Streamや再開による重複はidempotency markerでno-opにする。
- v1 Backfillは一回限りとし、完了checkpointのreset操作は設けない。再取込はprojection versionを
  上げる独立工程とする。
- response／log／artifactへcursor、source key、Debate ID、質問、本文を保存しない。
