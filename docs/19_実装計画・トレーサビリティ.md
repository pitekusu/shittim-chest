## 3. Change order

通常変更は次の順序で進める。

1. narrowest authorityで要求／境界を確認する。
2. domain／applicationの不変条件とfailureを先に決める。
3. adapter／CDK／workflowを必要最小限で変更する。
4. focused test、全local gate、canonical CIを実行する。
5. public-safeな正本だけを更新してmirrorする。
6. normal PR、review、required checks、CodeQL、squash mergeを行う。
7. 明示許可後にProduction Releaseと最小live acceptanceを行う。

途中で別原因、scope外resource、追加external writeが必要になった場合は同じ変更へ抱き合わせず停止する。

## 4. 1.0 Definition of Done

- `/shittim`からterminal表示までの全phaseをproductionで確認済み。
- participant 3人の相互認識、shared Evidence、匿名vote、Python winnerを確認済み。
- generation checkpoint、ordered Outbox、Status、retry／cancelが永続化される。
- farewellを通常channelへ送った後、ECS 0／0／0へ戻る。
- 5 stackがstable、deployment lock open、unexecuted Change Set 0。
- required CI、CodeQL 3言語、container supply-chain gate、docs gateが運用中。
- production secret／identifier／personaがpublic surfaceに存在しない。
- README、AGENTS、20正本文書がcurrent 1.0の実装と一致する。

token rotation、PITR restore、break-glass ECS Execはsoftware DoDではなく別のoperator drillとする。

## 5. Maintenance rules

- current contractを1つの領域文書へだけ置き、完了済み計画へ新仕様を追記しない。
- package／tool versionはlockfileを参照し、文書にpatch versionを重複固定しない。
- config／schema migrationはcurrentとpreviousだけを本文に残し、古い履歴はGitへ委ねる。
- image変更時は同一runのproduction／break-glass evidenceを確認し、静的baselineを再導入しない。
- live acceptanceは代表caseに絞り、障害注入と全組合せはlocal／contract testで担保する。
- runtime prompt互換層、ADMIN認可／status、prompt editor／historyは順に別PRとし、各Release後も
  active revision作成は独立した明示管理操作とする。
- 最初のADMIN Records Releaseより前にReleaseIdentity Stackだけを先行更新し、Records plan roleへ
  exact Runtime Stackの`cloudformation:DescribeStacks`を付与する。この更新を通常のRecords Releaseへ
  暗黙に含めず、反映確認後にPR-2をReleaseする。
