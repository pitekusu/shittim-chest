# 実装計画・トレーサビリティ

## 1. Current state

要求仕様、基本設計、監査修正後の詳細設計、STEP-01〜10、通知基盤、Discord受付・状態収束、Web Evidence、討論過程表示を実装済みである。Obsidian正本はGitHub `docs/`へ一方向mirrorし、Public repository、managed GitHub security、required CI、CodeQLを継続運用する。STEP-05C.1Bの比較結果を受け、本番PolicyはLuna standardだけへ固定し、回答差は3つのversion付きprivate persona promptで作る。Responses API Multi-agent betaは使用せず、winnerはPythonだけが決定する。

Stateful、Runtime、Operations、CostGovernanceの4 Stack、ReleaseIdentity、Discord HTTP Interactions Endpoint、4 Bot、`/shittim`はProduction Releaseで本番へ反映済みである。署名付きHTTP InteractionとDynamoDB永続FIFOが受付正本となり、ARM64 On-Demand Fargate serviceは通常`desiredCount=0`、最大1 taskで`0→1→0`へ収束する。初回意見、最終案、匿名投票、moderatorの票数・winner発表、winner personaによる最終発表、thread panelとchannel StatusのCOMPLETED収束を段階live acceptanceで確認済みである。release supply chainはdigest固定DHI image、SBOM、VEX、Grype、署名、attestation、image admission、fenced Change Set、deployment lock、drift検査を維持する。初回Release失敗とrollbackは解消済みの履歴であり、現在進行中のsoftware実装sliceはない。一方、Bot token rotation、DynamoDB PITR restore、break-glass ECS Execのlive drillは未実施であり、formal operational-readiness closureは未完了である。実施済み／未実施の証拠は[[20_実装・試験・検証記録]]のoperational drill evidenceを正とする。過去のFargate Spot常時1 taskは履歴であり、現行の実装定義ではない。

## 5. Definition of done

software実装と初回production acceptanceは完了している。formal operational-readiness closureは、次のlive drillが[[20_実装・試験・検証記録]]へ記録されるまで未完了であり、本書のfrontmatterも`operational-drills-pending`を維持する。

- Requirement traceabilityの全行に実装PR、test evidence、運用ownerが紐付く。
- CI、integration、formal E2E、fault injection、security、ARM64、CDK試験が合格する。
- Discord Application、AWS/GitHub設定が設計値と一致し、driftがない。
- dashboard、composite alarm通知、rollback／cleanup／deployment lockのlive evidenceがある。
- Bot token rotation、DynamoDB PITR restore、break-glass ECS Execのlive drillを各1回完了し、秘密値を含まない証拠を記録する（未完了）。
- production cost estimateとBudget notificationを確認する。
- 公式資料をdeploy当日に再確認し、URL、日付、version、差分をPR/ADRへ記録する。
- unresolved critical/high issueがなく、known issueがownerと期限を持つ。
- 各sliceのlocal/CI/deploy詳細はPull Request／Actionsへ保存し、最終合否、設計へ影響する原因、未実施範囲が[[20_実装・試験・検証記録]]へ要約され、Obsidian正本と公開mirrorが一致する。

詳細設計、実装、review、障害対応の各turnで一次資料を再確認する。AWS Developer Guide/API Reference/Pricing、Discord Developer Docs、OpenAI Developer Docs、Python公式、PyPI、library公式repository、GitHub Docsを使用し、guideとAPI shape/SDK typeを照合する。確認不能なら推測で確定せず作業を保留し、公式挙動との不一致はintegration testとADRへ残す。

## 7. Document responsibility・conflict handling

要求書は要求、意思決定記録は理由と受容risk、各詳細設計はinterfaceとfailure処理、試験設計は合否、本書は対応関係と順序を担当する。Pull Request／Actionsは各sliceの完全な実測証跡、[[20_実装・試験・検証記録]]は現行到達点・重要原因・最新受入・未解決事項の要約とする。矛盾時は実装を停止し、ADRへ選択肢、影響、決定日を記録して全関係文書を同時更新する。
