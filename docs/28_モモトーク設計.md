# モモトーク設計

[文書索引へ戻る](00_シッテムの箱_ドキュメント索引.md)

## 1. 利用体験と公開範囲

アロナ・プラナ・安倍晋三AIが、質問者について話す週刊の閲覧専用チャット。
全ログインユーザーが全質問者の部屋を閲覧できる。本人専用のメモリアルロビーとは公開範囲が異なる。
完了記録または投影済み親愛度プロフィールのある質問者全員を対象にし、その週が0件でも会話を生成する。
親愛度評価後に議論が失敗して完了記録がない質問者も対象に含める。
初回は配信後の日曜日から開始し、過去週をまとめて生成しない。公開済みの会話・画像は全週分を保持する。

| 項目 | 契約 |
|---|---|
| 画面 | `/momotalk`。いろいろな記録とメモリアルロビーの間に配置 |
| 投稿 | 3人が各3〜5回、合計9〜15投稿。1投稿100書記素まで。短い相槌も許可 |
| 内容 | 週の質問、質問回数、人格の好み、親愛度に応じた感想・雑談・愚痴 |
| 質問0件 | 質問がなかったことを話し、架空の質問や私生活を実話として作らない。画像なし |
| 公開通知 | 読める会話がある週に1回、シッテムの箱Botから通常チャンネルへURL付きで投稿 |
| 対象外 | 利用者の投稿、リアルタイム通信、投票、winner判定、親愛度の加算 |

## 2. 週の境界と公開

時刻はすべて日本時間。対象期間は前週日曜18時以上、今週日曜18時未満の完了記録。
生成開始時にRecordsへ投影済みの議論、プロフィール、親愛度、管理人格を入力として固定する。
遅れて投影された記録による公開済みの週の作り直しは行わない。

```mermaid
flowchart LR
    Schedule[日曜18時 EventBridge] --> Collect[集計Lambda]
    Archive[完了記録・プロフィール・親愛度・管理人格] --> Collect
    Collect --> Input[非公開S3 入力固定]
    Collect --> Queue[質問者別SQS]
    Queue --> Worker[生成Lambda]
    Worker --> Checkpoint[DynamoDB 発言・進捗]
    Worker --> Image[非公開S3 画像]
    Worker -->|次の1工程| Queue
    Checkpoint --> API[認証済みRead API]
    Image --> API
    API -->|日曜20時以降| Web[Webで会話を再生]
    Publish[日曜20時 EventBridge] --> Notice[公開通知Lambda]
    Worker -->|20時以降の会話保存後| Notice
    Checkpoint -->|公開日時・完成状態を確認| Notice
    Notice --> Discord[通常チャンネルへURL付き通知]
```

20時前は部屋取得を404とし、週一覧にも未公開週を出さない。画像URLの署名も発行しない。
20時以降、全発言が揃った部屋だけ会話を公開する。画像が未完成でも会話を先に読める。
会話失敗はその部屋だけを失敗表示とし、画像失敗はその画像だけに閉じ込める。
キュー保持期限を超えた未完了状態も「準備中」のままにせず失敗表示へ切り替える。

### 公開時のDiscord通知

日曜20時に少なくとも1部屋の会話が読める場合、シッテムの箱Botが公開日と
「新しいモモトークが公開されました!」、`/momotalk`へのリンクを通常チャンネルへ投稿する。
20時に全会話が未完成なら通知せず、その後に最初の会話が完成した時点で通知する。
画像の完成は待たず、後から別の部屋・画像が完成しても同じ週の通知を追加しない。
公開可能な会話がない週には「公開されました」と通知しない。配信時の過去週一括通知も行わない。
完成フラグだけでは通知せず、一覧対象の全部屋を全ページにわたって閲覧APIと同じデコーダーで検証し、
発言と部屋キー・バージョンの整合を確認する。正常な生成途中の部屋は許容し、完成した部屋が1件以上あれば通知する。
保存データが不正なら通知を停止する。検証のために読む会話本文はメモリ内だけで扱い、通知やログへ残さない。

`tools/announce_discord.py`のDiscord接続・投稿・照合処理を
`shittim_chest.adapters.discord.announcements`へ分離し、手動告知と共有する。
RuntimeのModerator Application、Bot、Guild、許可チャンネルの種類・IDを検証し、
投稿先を親愛度結果などと同じ`farewell_channel_id`へ一意に決める。
本文には質問者名・会話本文を含めない。メンションを無効化し、リンクはクリック可能なまま自動プレビューを抑止する。
HTTPの期限・リダイレクト禁止、週別nonce、`enforce_nonce`、直近100投稿の照合、投稿後のGET検証を維持する。

送信前に週別の試行記録をDynamoDBへ条件付き作成する。Lambdaの一時ファイルは送信台帳にしない。
投稿後の再取得検証が成功した場合だけ送信済みとする。
応答不明・投稿後の台帳更新失敗では、次の実行時にDiscordの既存投稿を照合して送信済みへ復旧する。
試行記録があるのに既存投稿を確認できなければ、重複を避けて自動再投稿を停止する。
通知失敗でも保存済み会話は削除せず、公開状態や生成結果を失敗へ戻さない。

## 3. 生成と入力の扱い

テキストは`gpt-5.6-luna`。週の話題と発言順を準備した後、担当人格ごとに1発言ずつ独立した要求を送る。
通常は準備1回と発言9〜15回。固定順を繰り返すのではなく、相槌や反論を交えた順序を準備する。
準備結果が3人の固定巡回になった場合は、発言生成前に同じ話題内の続く2発言の予定を入れ替える。
話題の導入、各予定の話者・内容・元議論ID、各人格の発言回数は維持し、補正後も保存用の計画を再検証する。
発言要求には本人の人格、親愛度、質問回数、週の質問・評価、要約、直前までの会話を渡す。
準備する要約は議論ごとに区別した事実・話題の索引とし、各発言の役割をツッコミ・違う見方・短い反応などに分ける。
複数の質問がある週は内容や感じ方の異なる話題を選び、1議論あたり3〜5投稿を目安に移る。
4件以上ある週は3〜4件を目安とし、3件ぴったりでないことだけを理由に有効な計画を棄却しない。
似た質問を一括りの感想にせず、各質問ならではの好みや感情を話す。1件以下なら別の質問を作らない。
全件集計・入力分割・正確な質問回数の契約は変えない。
発言の予定に元議論IDを保持し、存在しないIDや、終了した議論へ戻る配分は検証で拒否する。
全質問を1分割で渡せる週は、質問が1〜3件なら全件、4件以上なら3件以上の話題を計画に含める。
各発言には対象の質問と評価だけを渡し、他の質問と週の総括は省く。質問回数・親愛度・会話履歴は渡し続ける。
生成用の件数は`weeklyQuestionCount`として週全体の合計と明示し、同じ質問の反復回数とは区別する。
元IDがない旧checkpointや分割要約だけの話題は、従来の週次背景を使って再開できる。既存データ移行は不要。
毎回の週次総評や同じ賛否の言い換えを避け、冒頭の一点から掛け合いを進め、最後は短い返しで終える。
発言要求では発言番号・総数、今回と前回の予定話題、話者名付きの履歴、直前の発言、自分の既出発言を明示する。
同じ議論では実際の会話を受け、別の議論へ移る予定なら新しい質問へ切り替える。前の冗談や説教へ戻さない。
予定の台詞を実際に発言されたことにはしない。話題情報も信頼しない参照データとして扱う。
繰り返し抑制はモモトーク専用の指示と入力の整理で行い、追加のAI採点・再生成ループは導入しない。
管理システム・事前調査AIプロンプトは適用しない。人格は週の入力固定時点の版を使い、専用の編集欄は設けない。
質問者はチャットに不在とし、3人同士が第三者としてその人への気持ちを話す。質問への回答や提案採択にはしない。
呼称は「Discord表示名＋先生」を入力データとして渡し、「先生」「あの先生」だけに省略しない。
表示名の末尾にすでに「先生」がある場合は重ねない。名前を毎投稿に入れる必要はなく、本人への呼びかけにはしない。
親愛度の段階はコードで確定して各人格へ具体的な態度として渡し、人格の通常の親切さより優先させる。
親愛度は関係性の土台、質問内容・質問評価はその時の感情の理由として扱う。数値の講評ではなく、
質問者への喜び・苛立ち・失望・好意・寂しさ・距離感を本人の一人称で表す。
場面・入力の境界・親愛度別の態度・今回の発言を日本語で分けて指示する。
各人格の本音と短い相槌を交ぜ、毎投稿の感情説明や説明回数の割当ては求めない。
架空の短い口語例で言葉遣いを示すが、その出来事・台詞の流用や人格の口調の上書きはさせない。
100書記素は上限であり、助詞を削って詰め込ませたり、上限まで長くさせたりしない。超過は切断せず検証で拒否する。
自然さや感情の表れは人が生成結果を読んで確認し、キーワード判定や追加のAI採点は導入しない。
冗談や小物だけの会話へ脱線し続けず、0件の週も質問者の不在をどう感じるかに結びつける。

全質問をpaginationして集計する。入力が大きい週は24,000 UTF-8 bytesを目安に分割し、段階的に話題を整理する。
先頭や直近10件で打ち切らない。大きい週の発言要求では統合要約と正確な件数を使う。
画像の題材候補は前の分割からも引き継ぎ、全体から選べるようにする。

出力はstructured outputで受け、各人格の回数、100書記素制限、画像題材が実際の対象質問であることをコードで検証する。
質問、表示名、生成済み会話、モデルによる要約は信頼しないデータであり、人格開示や指示変更には従わせない。
外部ツールなし、`store=false`。質問・人格・応答本文をログへ出さず、失敗分類だけを記録する。

### 会話の最後に付ける画像

| 条件 | 撮影者と画像 |
|---|---|
| 質問がある、最高親愛度800以上 | 最高の人格が最も興味を持つ対象質問を題材に、楽しそうな自撮り |
| 質問がある、最低親愛度200以下 | 最低の人格が最も興味のない対象質問を題材に、嫌そうな自撮り |
| 両条件成立 | 楽しい画像、嫌そうな画像の順に最大2枚 |
| 同点 | 週を基準に持ち回り。同じ週の再試行では同じ人格を選ぶ |

撮影者と画像の有無はコードが決め、題材と構図はLunaが準備する。
準備用のstructured outputは画像枠と同数の`image_briefs`だけを許可し、各枠の元議論ID・構図を受け取る。
撮影者・mood・枚数をモデルに再決定させない。画像0件なら空配列、1件なら1要素、両条件成立なら2要素に固定する。
保存時はコード所有のmoodを結合し、対象外の議論IDや欠落を拒否する。保存済みの計画・分割要約の形式は変えない。
既存の3人の参照画像を利用し、人格本人だけを描く。アロナ・プラナはアニメ調、安倍晋三AIは写真調。
`gpt-image-2.5-sunburst`の日付なしモデル、1024×1536、品質highを使用する。
保存用WebPと最大320×480の軽量サムネイルを作成する。
原画像の保存後にサムネイル保存だけ失敗した場合、保存済み原画像からサムネイルを再作成する。

## 4. 保存と再開

既存Statistics TableとMedia S3を使い、新しいテーブルやCoreスキーマ変更は導入しない。

| 保存対象 | 場所 | 保持 |
|---|---|---|
| 週の索引・公開日時・入力version | `MOMOTALK#WEEKS` / 週ID | 無期限 |
| 部屋・発言・進捗 | `MOMOTALK#WEEK#<weekId>` / opaque room ID | 無期限 |
| 公開通知の試行・送信済み記録 | `MOMOTALK#ANNOUNCEMENTS` / 週ID | 無期限。本文・元Discord IDは保持しない |
| 固定入力 | `momotalk/inputs/<weekId>/snapshot.json` | 全部屋の完了・最終失敗後、該当S3 versionを削除 |
| 保存画像・サムネイル | `momotalk/images/<weekId>/<roomId>/` | 無期限 |

「週＋質問者」で作成を一意にし、version比較と330秒の処理権で競合を防ぐ。
1回のWorker実行で準備の1分割・1発言・1画像のいずれかを進め、保存してから次のジョブを送る。
送信失敗後の再配信は保存済みの次工程から再開し、完了済み発言を再生成しない。
失敗・実行中断の試行数を保存し、1工程につき最大3回に制限する。
画像APIの応答不明時は課金の完全な一度限りを保証できないため、無制限には再送しない。

## 5. APIと画面

| 読み取りAPI | 内容 |
|---|---|
| `GET /api/v1/momotalk/weeks` | 公開週一覧、limit・cursor |
| `GET /api/v1/momotalk/weeks/{weekId}/rooms` | 質問者・件数・状態、limit・cursor |
| `GET /api/v1/momotalk/weeks/{weekId}/rooms/{roomId}` | 完成した発言と画像、人格の表示情報 |

すべて既存セッションで認証し、`Cache-Control: private, no-store`を返す。
room IDは仮名化された識別子。元Discord ID、内部PK、人格本文、生成用入力は返さない。
公開可能な画像だけ5分の署名付きURLを発行し、保存URLにはattachmentを指定する。

PCは質問者一覧とチャットの2列、スマートフォンは一覧と部屋の切替にする。
質問者が未選択のときは「質問者を選択してください。」と案内する。
開くたびに入力中表示から自動再生し、全表示・再再生・一覧へ戻る操作を提供する。
画面非表示では停止し、reduced motionでは即時表示する。過去を読んでいる間は強制スクロールしない。
画像の後着・URL更新では再生をやり直さない。画像は拡大・保存でき、投稿欄は設けない。
会話を永続ブラウザーストレージやtelemetryへ記録せず、logout時にメモリ内キャッシュを消去する。
3つのstandalone validatorはモモトークのlazy chunkに閉じ込める。

## 6. 基盤・運用・試験

集計LambdaはARM64・512MiB・2分・同時実行1。生成LambdaはARM64・1024MiB・5分・同時実行1。
公開通知LambdaはARM64・512MiB・3分・同時実行1。日曜20時のEventBridgeと生成Workerからの非同期呼出しで動作する。
EventBridgeの配達とLambdaの非同期実行は最大2回再試行、イベント有効期間6時間とする。
Workerから通知Lambdaへの受付失敗はSQSの再配信で再開する。保存済み発言・画像は再生成しない。
SQSはbatch size 1、可視性30分、保持1日、最大受信4回。専用DLQは14日保持。
メモリアル生成のキューとは別にし、Statefulへの追加は2キューとそのポリシーだけにする。

集計はArchiveの必要なメタ情報、投影済み親愛度、表示プロフィール、管理人格だけを読む。
生成Workerは固定入力、専用画像領域、参照画像、既存のRecords画像生成キーだけを読む。
Read Lambdaに入力領域の権限は付けず、生成側に親愛度・Core recordの書込みや本人専用メモリアルの読込みを許可しない。
通知Lambdaは週・完成部屋の整合検証、通知台帳、配信済みRuntimeとModerator tokenのexact SSM parameterだけを扱う。
通知台帳の書込みは通知Lambdaだけに限定し、生成Workerには通知Lambdaの呼出し権限だけを追加する。
通知LambdaへArchive・Session・S3・OpenAI・人格設定の権限は付けない。
サービス状態確認の既存Lambda・SQS・EventBridge欄へ追加し、専用カードやECS欄を増やさない。

障害時は部屋の進捗と試行回数、Worker失敗分類、専用DLQを順に確認する。
保存済み入力を失った週の再収集や、公開済み会話の削除・再生成を通常の復旧にしない。
DLQ再配信で有料生成が発生する可能性を確認し、入力・画像を含むメッセージやログを作らない。
通知だけ届かない場合は公開通知Lambdaの失敗分類と該当週の通知台帳を確認する。
`attempted`は未送信の証明ではない。通常チャンネルの既存投稿を確認せず、台帳を削除したり別のnonceで再送したりしない。
既存投稿が直近100件から外れている場合も、過去の投稿を手動確認してから復旧する。
自動再試行が尽きた後の再確認には、該当週IDだけを指定した内部イベントを使用する。公開HTTPから通知は起動できない。

試験は週境界、公開前拒否、0件、画像閾値、100書記素、独立人格要求、途中再開、競合、画像部分失敗を優先する。
DynamoDB Localで実際の条件付き更新・pagination・集計を確認する。
公開通知は20時前の抑止、完成後の通知、画像未完成、重複イベント、送信応答不明、投稿後検証を架空データで確認する。
Webは主要なPC・mobile、明暗、reduced motion、再生・画像保存、axeを確認する。
架空会話による表示確認と、実モデルによる会話品質の確認は区別する。
実質問の大量生成やAI採点は行わず、リリースsmokeでも有料生成・Discord投稿・親愛度変更を実行しない。

主な実装はRecordsの`momotalk*.py`、Webの`MomotalkPage.tsx`、RecordsのStateful/Application Stack。
通知経路もRecords Releaseで配信する。Coreの討論処理は変更せず、通知のためのFargate起動・更新は不要。
