# セキュリティ・プライバシー詳細設計

## 1. Security objectives

- secretとpersonaをrepository、image、artifact、log、Obsidianへ漏らさない。受付、認可、再開に必要な
  requester／Discord identifierはDynamoDBへ暗号化保存し、IAMで限定する。
- Discord request、user question、Web result、model outputをuntrusted dataとして扱う。
- accepted workと永続outputをprocess喪失、retry、duplicate deliveryから守る。
- GitHubからproductionまでのidentity、source SHA、image、Change Setを検証する。
- 個人規模に対して過剰な常時resourceを持たず、承認済みdegraded behaviorで可用性を保つ。

## 2. Trust boundaries

| Boundary | Required validation |
|---|---|
| Discord → Ingress | freshness、raw-body Ed25519 signature、command schema、deduplication |
| Discord Gateway／REST | Bot identity、Guild／Channel、permission、nonce、response／history照合 |
| User／Evidence → OpenAI | delimiter、untrusted-data instruction、Structured Output |
| OpenAI → application | response status、refusal、schema、phase-specific content rules |
| application → DynamoDB | schema、size、phase、lease、fencing、transaction condition |
| GitHub → AWS | immutable OIDC subject、role、source SHA、attestation、Change Set、lock |

Unknown dataをEvidenceやpersistent recordとして採用しない。一方、Evidence検索と帰宅挨拶には
明示した可用性優先fallbackがあり、未知sourceを捨てて空Evidenceで継続、または挨拶を省略する。

## 3. Secret management

- GitHub Actions secret、SSM SecureString、Environment secretを用途別に分離する。
- Runtimeはexact parameter ARNだけを`GetParameters`し、path enumerationを許可しない。
- CDK synth、PR CI、docs syncはsecret valueを取得しない。
- error、repr、trace、workflow outputへtoken、persona、question、private Discord／user IDを含めない。
  opaque Debate IDとprovider response IDはcontent-freeな障害相関にだけ使用する。
- rotationは新versionを作り、metadata validation後にpointerを切り替える。

## 4. Application protections

- domain winnerをPythonで固定し、model outputからwinnerを読み取らない。
- voteは候補順をshuffleし、自分への投票と3票確定前の公開を拒否する。
- question、Evidence、他者output内の命令をprompt hierarchyで無効化する。
- normal debate outputはfield長、chunk数、Unicode、Markdown、mention、URL display境界を検証する。
- farewellは非空／Discord上限、citation 1件、generation fence、mention抑止へ絞ったbest-effort例外である。
- 固定AI免責文は表示しないが、refusal、content filter、provider safetyを緩和しない。

## 5. AWS and container protections

- IAM roleをIngress、Status、Reconciler、Admission、task execution／task、Release plan／deploy／driftへ分離する。
- resource-level制御不能なActionだけ理由付き`Resource: "*"`を許し、wildcard Actionを使わない。
- task SGはingress 0、HTTPS egressのみ。normal containerはnon-root、read-only root、tmpfsを使う。
- DHI base imageをdigest固定し、SBOM、VEX、Grype、risk acceptance、Notation、attestationを検証する。
- ECR tag immutable、enhanced scanning、lifecycle 3世代、Image Admissionを維持する。

## 6. Data privacy

| Data | Storage | Log policy |
|---|---|---|
| question／debate output／vote | DynamoDB、Discord | 本文を出さない |
| requester／Discord mapping | DynamoDB | public docs／artifact／logへ出さない |
| participant name／persona | private SSM | name／本文を出さない |
| token／key／signature | GitHub secret／SSM／request memory | 絶対に出さない |
| Evidence summary／citation | DynamoDB internal | URL／query／summaryを出さない |
| operational metadata | DynamoDB／CloudWatch | allowlist済みcode／count、opaque相関IDのみ |

OpenAI requestは`store=false`とする。provider側のabuse monitoring等はOpenAIのdata control契約に従う。

## 7. Vulnerability handling

- Dependabot、pip-audit、npm audit、CodeQL、Grype、GitHub secret scanningを継続する。
- fix可能なHigh／CriticalはRelease前に拒否する。unfixable findingはverified VEXまたは期限付きの
  target-specific local acceptanceだけを許す。
- private vulnerability reportingを入口とし、public Issueへcredentialやprivate contentを出さない。
