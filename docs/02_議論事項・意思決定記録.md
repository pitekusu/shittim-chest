# 議論事項・意思決定記録

本書は現行1.0を説明するADRの要約である。検討過程、PR単位の作業記録、完了済み
実装計画はGit historyへ委ねる。

## ADR-01 Python orchestration

- **決定**: phase遷移、並列生成、投票、winner、retryをPythonが管理する。
- **理由**: deterministicなwinnerと再開可能なdurable stateを保つため。
- **棄却**: modelによる勝者選択、Responses Multi-agent betaへのorchestration委譲。
- **再検討**: 永続化、匿名投票、winner規則を同等以上に検証できるstable APIが必要。

## ADR-02 private personaと共通名簿

- **決定**: generic slotだけをcodeへ置き、display nameとpersonaをversion付きprivate設定で渡す。
  初回意見、最終案、winner発表では全員の名簿を共有し、投票は匿名のままとする。
- **理由**: 相互認識と人格維持を両立し、private設定をrepositoryから分離するため。
- **棄却**: personaのsource管理、各Botへ別process、投票時の実名候補。

## ADR-03 shared agentic Evidence

- **決定**: 全議題で共通Evidence Agentを1回実行し、`web_search`の使用はmodelが判断する。
  既知の検索失敗は空Evidenceへdegradeし、個別participantにはtoolを与えない。
- **理由**: deterministic routerの誤分類を避け、費用と参加者間の情報差を抑えるため。
- **棄却**: 正規表現Question Router、各participantの独立検索、検索失敗で討論全体を停止。
- **安全境界**: 未知sourceはEvidenceへ採用せず、unclassified programming errorは隠蔽しない。

## ADR-04 Discord HTTP ingressとGateway runtime

- **決定**: command受付は署名付きHTTP endpoint、投稿とBot identityは稼働中Gatewayで扱う。
- **理由**: Fargate task 0でもDiscordの応答期限内に耐久受付するため。
- **棄却**: Gateway常駐受付、Lambdaからの全投稿、Interaction tokenの永続保存。

## ADR-05 Scale-to-Zero singleton

- **決定**: ARM64 On-Demand Fargateを平常0、必要時1、最大1 taskで運用する。
- **理由**: 仲間内利用の可用性を保ちながら常時費用を避けるため。
- **棄却**: Fargate Spot常時1、Provisioned Concurrencyによる受付常時warm、複数Runtime。
- **境界**: signed HTTP ingressとSnapStart Lambdaがcold-start UXを担当する。

## ADR-06 durable checkpoint and Outbox

- **決定**: generation checkpoint、phase delivery plan、global sequence付きOutboxをDynamoDBへ保存する。
- **理由**: model call／Discord POSTの境界でprocessを失っても、永続結果と表示を重複させず
  terminalへ収束するため。
- **棄却**: process memoryだけの討論、provider-level exactly-onceへの依存。

## ADR-07 availability-first farewell

- **決定**: idle停止予定約5分前に1 participantが通常channelへ挨拶する。Web citation 1件を
  最低条件とし、生成／送信は各最大2回、best-effortとする。
- **理由**: SIGTERM直前の処理と厳密すぎるsource照合で欠落した経験から、停止と分離して
  可用性を優先するため。
- **棄却**: shutdown hookでの送信、複数sourceの完全一致、挨拶失敗によるtask残留。

## ADR-08 data and logging

- **決定**: debate本文はDynamoDBとDiscordへ必要範囲で保存し、運用logはcontent-freeにする。
- **理由**: crash recoveryに必要なdurabilityと、private会話の露出最小化を両立するため。
- **棄却**: raw request／model responseのlog、persona本文のrepository保存。

## ADR-09 five-stack CDK ownership

- **決定**: Stateful、ReleaseIdentity、Runtime、Operations、CostGovernanceへ責務分割する。
- **理由**: retained data、GitHub OIDC identity、runtime、monitoring、global cost resourceの
  lifecycleとregionを分けるため。
- **境界**: 通常Releaseは4 application stackを更新し、ReleaseIdentityは先行更新が必要な場合だけ
  独立工程で扱う。

## ADR-10 attested Production Release

- **決定**: OIDC role、digest固定image、SBOM、VEX、Grype、risk gate、Notation、GitHub
  attestation、immutable Change Set、deployment lockを用いる。
- **理由**: buildしたartifactとdeploy対象を結び、手動AWS writeを通常経路から外すため。
- **変更済み判断**: PRの静的config digest baseline一致とCI artifactとのcross-run完全一致は
  可用性を損なうため廃止した。各run内の両target実測とrisk gateは維持する。

## ADR-11 user-facing expression

- **決定**: winnerはprivate personaに沿って大げさな喜びを示す。全terminal表示の固定AI免責文は
  仲間内利用では表示しない。
- **維持する境界**: provider safety、Structured Output、Python winner、untrusted-output処理は
  表現方針にかかわらず緩和しない。

## ADR-12 documentation authority

- **決定**: public-safeなObsidian notesを正本、GitHub `docs/`をexact mirrorとする。
- **理由**: private operator情報を分離しつつ、実装者が同じ公開設計を参照できるため。
- **運用**: 現在契約だけを領域文書へ一度記載し、PR/run履歴はGitHubへ委ねる。
