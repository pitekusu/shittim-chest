# 運用保守・監視・障害対応設計

GitHub Actions、Dependabot、CodeQL、GrypeのDiscord Forum通知と通知経路自体の停止検知は[[21_GitHub・Discord通知運用設計]]に定める。この通知はGitHubの正式なcheck・Security tab・Actions logの代替ではない。

Scale-to-ZeroとDiscord受付はproductionへdeploy済みであり、Discord ApplicationのInteractions Endpoint切替、通常討論の完了、停止時ECS `0/0/0`までlive確認済みである。本文のlive runbookは現行production運用に適用する。

## 1. Service objective

MVPに外部SLAは設定しない。On-Demand Fargateは平常`desiredCount=0`、依頼・復旧workがある間だけ最大1 taskとする。STOPPED/IDLEとtask 0は正常であり、起動中・処理中は4 Bot READY、受付済みdebateの再開可能性、永続化と投稿の整合性を運用品質の中心とする。

目標値は月次で、受付済みdebate成功率95%以上、application起因の失敗率5%未満、active processingのp99 300秒以内とする。cold start時間、3分を超えた件数、3〜15分で復旧した件数、15分terminal件数、完全終了からscale-downまでの時間を別集計する。

## 2. Structured logging

JSON logの共通fieldは`timestamp`、`level`、`event`、`service`、`version`、`debate_id`、`phase`、`attempt`、`duration_ms`、`error_code`、`aws_request_id`とする。Discord/OpenAI本文、token、authorization header、full SDK request/responseは記録しない。

`ingress_retry_scheduled`は`delivery_attempt`、`error_code`、`retry_delay_seconds`、`retry_delay_source`を残す。`terminal_delivery_conflict`はtransaction stage、allowlist済みfailed action kind／cancellation code、reason completeness、retryable、retry番号／delayを残す。これにより再Releaseなしで429待機値とterminal transactionの失敗箇所を区別できる一方、Discord response body/header、DynamoDB item/condition、質問や生成内容は保存しない。

- application log group: retention 90日、CloudWatch Logsのservice-managed暗号化、streamはtask ID単位。
- break-glass ECS Exec log group: retention 90日、application logと分離。平常taskからは書き込めない。
- 両log groupへCloudWatch Logs data protection policyを適用し、credential・identifier patternをaudit/maskする。
- UTCで記録し、dashboard表示だけJSTを使用する。
- exceptionは型、code、retryability、stack traceを記録し、secret redaction filterを通す。

## 3. Metrics

namespaceは`ShittimChest/Prod`とする。STEP-09C-Aの初期custom metricはCloudWatch Embedded Metric Formatを既存CloudWatch Logsへ1 JSON document/標本で出力し、dimension setは固定の`[["Service"]]`だけ、値は`runtime`または`reconciler`だけとする。`Environment=production`はroot propertyでありdimensionではない。debate ID、user ID、thread ID、Guild/channel/Application ID、質問、回答をdimensionにもfieldにも含めない。standard resolution 60秒を使い、task/Lambda roleへ`cloudwatch:PutMetricData`を付与しない。

| Metric | Unit | Purpose |
|---|---:|---|
| `BotReady` | Count | task稼働中に4 BotすべてREADYなら1、いずれか非READYなら0。60秒ごとに本文なしで発行。task 0では欠測が正常 |
| `HeartbeatAgeSeconds` | Seconds | task稼働中のevent loop heartbeatからの経過秒。task 0では欠測が正常 |
| `RuntimeStateCode` / `RuntimeDesiredCount` | Count | `unknown=0`、STOPPED=1、STARTING=2、READY=3、BUSY=4、IDLE=5、STOPPING=6、DEGRADED=7とdesired 0/1の不一致を検出 |
| `EcsRunningCount` / `EcsPendingCount` | Count | singleton ECSのobserved running/pending 0/1をReconciler標本へ含める |
| `IngressPending` | Count | PENDING/CLAIMED/RETRYINGの合計。最古ageは追加queryとmetric費用を正当化できた場合だけ別sliceで追加する |
| `ReconcilerFailed` / `StatusPublishFailed` | Count | 1分Reconcilerと公開Status Message更新の異常 |
| `ECS CPUUtilization/MemoryUtilization` | Percent | Fargate Serviceが無料で送る標準ECS metric。飽和・異常傾向の確認用 |
| `OutboxPending` | Count | PENDING/CLAIMEDの合計。最古ageは追加queryとmetric費用を正当化できた場合だけ別sliceで追加する |
| ECS task `STOPPED` | Event | EventBridgeのtask停止通知。STOPPING/STOPPEDへの計画停止と、STARTING/BUSY中の予期しない停止を区別 |

## 4. Alarm definition

| Alarm | Condition | Period・M-of-N | Missing data | Severity |
|---|---|---|---|---|
| Bot not ready | runtimeがSTARTING/BUSY/DEGRADEDかつrunning task 1で`BotReady < 1`または標本停止 | 60秒、2/3 | underlyingはbreaching、active runtime composite外では通知なし | critical |
| Heartbeat stale | runtimeがSTARTING/BUSY/DEGRADEDかつrunning task 1で`HeartbeatAgeSeconds > 60`または標本停止 | 60秒、2/3 | underlyingはbreaching、active runtime composite外では通知なし | critical |
| Task stopped unexpectedly | 対象cluster/serviceのECS task `STOPPED`かつ異常系stop code | eventごと | 該当なし | warning |
| Runtime convergence | pending > 0でdesired 0、または完全空状態で30分経過後もdesired 1 | 60秒、2/3 | notBreaching | critical |
| Ingress/runtime mismatch | `IngressPending > 0`かつ`RuntimeDesiredCount = 0` | 60秒、2/3 | notBreaching | critical |
| Reconciler failure | `ReconcilerFailed >= 1` | 60秒、1/3 | notBreaching | critical |
| Status publish failure | `StatusPublishFailed >= 1`が3標本中2回 | 60秒、2/3 | notBreaching | warning |
| Outbox backlog | `OutboxPending > 0`が10分継続 | 60秒、10/10 | breaching | warning |
| DynamoDB throttle | service metric `> 0` | 60秒、1/3 | ignore | warning |

STOPPED/IDLE、desired 0、running 0での`BotReady`と`HeartbeatAgeSeconds`欠測は正常とする。health underlying alarmは欠測をbreachingとするが、runtime stateがSTARTING/BUSY/DEGRADEDかつrunning task 1のalarmとANDしたcritical compositeだけが通知するため、task 0では通知しない。EventBridgeは`TaskFailedToStart`、`EssentialContainerExited`、`SpotInterruption`、`TerminationNotice`だけを通知し、計画停止で使われる`UserInitiated`と`ServiceSchedulerInitiated`を除外する。Runtime alarm、AWS Budget、Cost Anomaly Detectionのactionは同じdeploy時必須operator emailへ送り、本文・secretを含めない。実addressは公開sourceへ保存しない。

## 5. Dashboard

1画面にruntime state、ECS desired/running/pending、Ingress pending、Bot READY、heartbeat age、Outbox pending、Reconciler/status publisher failure、ECS CPU/Memory、DynamoDB throttle、alarm statusを配置する。deployment annotationにはcommit SHAとimage digestを記録する。task 0の時間帯は「欠測」ではなくSTOPPED/IDLEとして読める表示にする。

## 6. Health・startup

container health checkはtask固有tmpfs上のevent-loop heartbeat鮮度だけを検査し、Discord/OpenAI障害でcontainerを再起動ループさせない。check processはstdlib-onlyの独立moduleで3秒以内に終了し、欠落、不正時刻、期限切れをcontent-freeな安定exit codeでfail closedにする。HTTP受付はtask 0やBot非READYでも署名・認可・queue条件が正常なら永続化する。runtime drainerは4 Bot READYかつrepository利用可能になってから開始する。起動時に設定、Parameter参照、table schema compatibilityを検証し、不足時はfail closedで終了する。recoverable attemptはlease取得後、討論phaseより先にpending outboxをdrainする。未来retry/claim待機中も20秒lease heartbeatを継続し、`discord_outbox_recovered`と`discord_outbox_retry_scheduled`を本文なしで計測する。

## 7. Runbook

### On-Demand scale-to-zeroとcold start

DiscordIngress Lambdaは署名・認可・冪等性・FIFO 20件上限を検証し、Ingress Requestを永続化してから即時に受付応答する。Reconcilerは1分ごとにpending requestとruntime stateを確認し、desiredCount=0のままならgeneration付きでSTARTINGへ遷移して1へ収束させる。重複起動、ECS API失敗、STOPPING中の新規requestでもCASとgenerationにより最大1 taskを維持する。

- 受付から2分59秒まではSTARTING表示を維持する。
- 3分時点でstartup timeoutをStatus Messageへ表示するが、requestはterminalにせずqueue件数に含めたまま起動・復旧を継続する。
- 3分から15分未満で実行開始できた場合はRECOVERED表示へ更新し、通常フローへ戻す。
- 15分時点でも未実行のrequestはterminal `FAILED`とし、queue counterをtransactionで減らし、後日実行できない。

すべてのIngress、debate task、lease、recovery、outbox、Status Message/panel更新が解消した場合だけIDLEへ遷移し、`stop_eligible_at=now+30分`を一度だけ固定する。29分59秒では停止せず、30分以降の1分Reconcilerでgeneration不変・空状態を再検証してdesired 0へ変更するため、実停止は通常30:00〜30:59に収束する。停止直前の新規requestはgenerationを進めてSTARTINGへ戻し、stale scale-downを拒否する。

停止予定2分前から同一IDLE generationにつき最大1回、participant 1人の帰宅挨拶をprocess内で先行生成する。top-level responseが`max_output_tokens`で未完了の場合だけ追加1 requestを許可し、成功時はretry回数と先行する未完了理由、失敗時はresponse／message／Web searchの段階と安定reasonをcontent-free telemetryへ記録する。正常な30分IDLE停止のSIGTERMだけでRuntime Stateを再確認して送信し、手動停止、異常終了、起動不要停止、generation変更では送信しない。検索、生成、権限、Discord送信・照合が失敗しても挨拶を省略し、shutdownとscale-to-zeroを継続する。本文、source URL、persona、channel IDをlogへ出さない。

SIGINT/SIGTERMを受けたcallbackは即時に新規drainとoutbox送信開始を停止する。readiness monitor、進行中task、startup recovery taskをcancel・awaitし、同一phaseのcheckpoint、controller close、4 Discord client closeをapplication内部90秒以内に行う。ECS側は`stopTimeout=120`とし30秒の終了余裕を残す。次taskは4 READY後にpending outboxをdrainしてからphaseとIngress Requestを再開する。

STEP-07Cのproduction processは起動設定をSDK client作成前にfail closedで検証し、設定不正を`startup_configuration_invalid`、実行失敗を`runtime_failed`として本文なしで出力する。content-free telemetryはevent名、時刻、model/Policy ID、token/latency/response ID等の許可済みmetadataだけを記録し、質問、回答、persona prompt、credentialを記録しない。実subprocess試験でSIGTERM時のcheckpoint/cleanupと、SIGKILL後にreplacement processが永続active stateを検出して回復できることを確認する。container/ECS境界はSTEP-08で追加検証する。

1 Bot切断時はRuntimeの新規Ingress claim/drainを即時停止する。60秒未満の一時切断では進行taskを維持し、60秒連続切断でtaskをcheckpointして待機する。HTTP永続受付はqueue上限まで継続する。通信断を`FAILED`へ変換せず、4 READY復帰後にfenced leaseを取得して自動resumeする。recovery taskまたはreadiness monitorが例外終了した場合はdrain gateを閉じ、processを異常終了させてECS schedulerの置換対象とする。

checkpoint永続化が失敗した場合はprocess errorとしてalarm対象にするが、Discord clientとsignal handlerのcleanupは継続する。次taskはlease expiryとfencingに従って最後に永続化済みのphaseから再取得し、旧workerのwriteを拒否する。

### Stuck lease

owner、lease expiry、fencing token、最新checkpointを確認する。期限前に手動解除しない。期限後は新workerがconditional updateで取得し、旧tokenのwriteが拒否されることを確認する。

### Outbox不整合

oldest pendingをgeneric Bot slot、nonce、content hash、chunk sequence、Discord message IDで照合する。`next_retry_at`または`claim_expiry`未来値なら期限まで待ち、期限前にclaimを手動解除しない。送信済みなら同一Bot author/nonce/contentのthread履歴を採用してmessage IDを条件付き保存し、未送信なら同じnonceで再送する。同一nonceの内容不一致、locked thread、権限不足は自動retryせずstable error codeとattemptを確認する。DynamoDB recordを直接削除して解消しない。

### Bot token rotation

production taskを停止し、Developer Portalで対象BotのtokenをresetしてSecureStringを更新する。stop-before-start deploy、4 READY、smoke testを確認してから次のBotへ進む。旧新tokenの同時有効を前提にせず、4つを一度にrotateしない。

### OpenAI model利用不能

model availability、project permission、status、SDK error codeを確認する。文書で承認していないmodelへ自動fallbackしない。代替modelは互換性・品質・費用試験後に設定を変更する。

### Discord権限剥奪

対象Guild/channelのView Channel、Send Messages、Create Public Threads、Send Messages in Threadsを確認する。Botを再招待する前にunexpected ownership/config変更がないか監査する。

### DynamoDB PITR

新tableへ35日以内の指定時点で復元し、schema/version/countを検証する。recovery CDK手順でtag、PITR、deletion protection、alarm、IAM resource ARNを再適用し、task roleと参照tableを同一change setで切り替える。production taskを停止して切替え、smoke test後も元tableは原因確定まで保持する。35日より古い状態は復旧対象外とする。

### Failed deploy

CloudFormation eventとECS deploymentを確認し、stateful replacementがあれば停止する。Runtimeはdeployment lockを保持したまま直前の正常digest/task revisionへrollbackし、recovery/outbox smoke testを行う。rollbackとsmoke完了後にだけ、取得時と同じguard ID、owner/actor、fencing tokenでlockをreleaseする。

release helperはplan開始時、plan失敗、deploy finally、独立cleanup jobのいずれでも、manifestのexact change set ARN、当該plan attemptのexact name、または4固定stackに残る正規名の未実行`release-*`だけを対象にする。開始時sweepはCLI自動paginationの全page、Stack/ChangeSet ARNの同一account/Region、current attempt不在、non-nestedを検査し、list snapshotだけで削除せずdescribeで状態を再確認する。`CREATE_PENDING`/`CREATE_IN_PROGRESS`と`DELETE_PENDING`/`DELETE_IN_PROGRESS`を有限pollし、未実行`AVAILABLE`/`FAILED` setを削除後、`ChangeSetNotFound`と全件再列挙の双方で消失を確認する。partial create直後の未検出は3回連続確認し、AccessDenied、Validation、transient provider errorを不存在として扱わない。実行中・実行済み・実行失敗、nested、未知状態は削除しない。manifest回収では実行中/実行失敗を記録して後続固定stackの未実行setを先に収束させ、その後cleanup全体を失敗させる。obsolete setは対象外とする。

failed-jobs-only rerunではplan artifactのattemptと新しいrun attemptが一致しないためdeployを開始しない。cleanup artifactの取得失敗時も、plan成功なら検証済みの旧`plan_attempt`からexact nameを再構成して回収し、plan失敗時だけcurrent attemptを使う。旧attempt回収は先行stackの`EXECUTE_COMPLETE`/`OBSOLETE`を安全にskipして後続の未実行setを処理し、`EXECUTE_IN_PROGRESS`/`EXECUTE_FAILED`は削除せず停止する。plan出力または取得済みmanifestが不正ならfallbackで成功扱いしない。cleanup後も意図的に失敗として残し、GitHub UIの`Re-run all jobs`で新しいplan、image tag、manifest、change setを作る。同じimmutable tagへの再push、旧artifactの流用は禁止する。

Runtimeが`ROLLBACK_COMPLETE`なら更新で再利用せず、operation-scoped failure eventとresource状態を確認してstackを削除する。旧templateの`Retain`で残った明示LogGroupは、Runtime stack/resource不在、log stream 0、stored bytes 0を再確認し、既知のexact 7 nameだけを削除する。新templateの`RetainExceptOnCreate`は初回create rollbackだけ削除し、通常delete/update replacementではretainする。

### Deployment guard・expired lock

現在の`production-deploy-guard.yml`は固定11 control recordをread-onlyで検査する診断workflowであり、lock acquire、deploy、releaseを行わない。`release.yml`は`acquire -> change set/deploy/smoke/必要なrollback中hold -> finallyでexact release`を一つの非cancel critical sectionとして実行する。通常はSTOPPED/IDLEだけを許可する。

workflowが停止してlock期限を超えても自動reclaimしない。GitHub run、CloudFormation、ECS、smoke/rollback状態を先に確認し、取得時の完全一致するguard ID、owner/actor、fencing tokenが証跡から復元できる場合だけidempotent releaseしてimmutable auditを残す。metadata不明、既存lock、malformed/missing control recordではfail closedのままincidentへ移行し、force unlockや新しいownerでの上書きを行わない。

deployment break-glassは理由`incident-response`、`security-investigation`、`service-recovery`とactor/run/commit/事前stateを必須とし、runtime state条件だけをoverrideできる。既存deployment lockはoverrideできない。これは、shell/Exec agentを持つECS Exec break-glass task revisionとは別手順・別監査である。

### Control-record manifest

最初にproductionへ導入するmanifestはv2で、9 activity record、runtime state、deployment lockの固定11 recordを原子的に初期化・検証する。manifest v1はlocal履歴だけでAWSへdeployされていない。v1 marker、partial record、未知versionはonlineで修復せずfail closedとし、task停止、backup/証跡取得、offline migration、v2再検証後に再開する。

### Image署名・OCI artifact異常

deployを開始せず、対象image digest、Signer profile ARN、`describe-image-signing-status`、Notation strict verification、`list-image-referrers`、scan resultを確認する。tagを付け直したり同じimmutable tagへ再pushせず、原因修正後に新しい一意tagと新digestでreleaseを作り直す。署名がrevoked/invalid、期待profileでない、SPDX/provenance/vulnerability assessmentが不足、subject/artifact digest不一致の場合は例外deployしない。既に稼働中digestの署名revocationまたはcritical findingを検出した場合はRuntimeの新規claim/drain停止、影響評価、直前の検証済みdigestへのrollbackまたは修正版release、incident記録の順に行う。HTTP受付自体を停止する場合は別のincident操作とし、queue内Requestの扱いを明示する。

### ECS Exec

通常調査で使わず、log/metricで不足する場合だけ承認する。production taskを停止し、write可能root filesystem、Exec agent、shell utility、限定task roleを持つbreak-glass revisionへ切り替える。MFA付き短期credentialで接続し、読取中心、開始・終了・実行理由をincident記録へ残す。調査後は平常のread-only/Exec無効revisionへstop-before-startで戻し、Exec agentがないことを確認する。API callはCloudTrail Event History、session内容は専用90日log groupで監査する。

### GitHub scheduled workflow停止

Public repositoryで60日間activityがない場合、GitHubはscheduled workflowを自動無効化する可能性がある。`dependency-graph.yml`と将来の`drift.yml`を唯一の監視経路とみなさない。月次にActions API/UIでworkflowの`state=active`と直近runを確認し、無効ならmaintainerが再有効化してmanual runを実行する。欠落期間、再有効化時刻、manual run結果を[[20_実装・試験・検証記録]]またはincident記録へ残す。

Container Insightsは無効であり、account defaultも変更しない。STEP-09C-Aでnamespace、固定`Service` dimension、10 metric allowlist、60秒Runtime標本、Reconciler invocation標本をコードとunit testへ固定した。Runtime readiness probeは10秒でtimeoutして`BotReady=0`、event-loop heartbeat fileが不存在・未来時刻ならageを発行しない。Reconciler成功はstate/desired/ECS/Ingress/Outboxとfailure 0を発行し、失敗は`ReconcilerFailed=1`、Status trigger失敗時だけ`StatusPublishFailed=1`を発行する。STEP-09C-Bで9 metric alarm、2 composite alarm、ECS/DynamoDB標準metricを含むdashboard、単一SNS topic/email subscription、異常stop code限定EventBridge ruleをcredentialなしsynthまで実装した。STEP-09C-Cで`us-east-1`の独立CostGovernance stack、2 Budget、既存AWS managed service monitorを参照するCAD subscriptionをcredentialなしsynthまで実装した。EMF抽出、SNS確認、alarm/event受信、Budget/CAD email到達、旧手動通知撤去はdeploy後受入であり、local合格と同義にしない。

## 8. Maintenance

- daily: alarm、Project 20 USD/account 30 USD/OpenAI 50 USD Budget、10 USD以上のCost Anomaly Detection確認。旧手動Budget/CAD通知が新CDK管理通知の到達確認後に撤去済みであることを移行時に確認する。
- weekly: dependency/security PR、ECR finding、CDK drift、failed/recoverable debate、稼働中/直前正常digestの署名状態・4種OCI referrer確認。
- weekly: DHI Docker Dependabot daily runの失敗、DHI・Docker Scout認証、full/actionable Grype差分、未修正High/CriticalのVEX/acceptance coverageを確認する。fix利用可能時は期限前でもacceptanceを廃止して更新PRを優先する。
- monthly: cost/SLO、IAM Access Analyzer finding、cost allocation tag、log data protection、runbook連絡先、GitHub scheduled workflowのactive stateと直近run、DHI Communityのsupport/release状態、risk acceptanceのowner/根拠/期限/対象digestを確認。
- quarterly: token rotation drill、PITR restore drill、scale-to-zero wake/stopとdeployment lock復旧drill、least-privilege見直し。
- deploy前: Discord/OpenAI/AWS仕様、model、料金、package version、DNS A/AAAAを再確認する。
