# 運用保守・監視・障害対応設計

## 1. Normal states

外部SLAは設定しない。平常のsafe stateは次である。

- Stateful、ReleaseIdentity、Runtime、Operations、CostGovernance stackがstable。
- ECS serviceはdesired／running／pendingが0／0／0。
- Runtime controlはSTOPPED、durable activityはclear。
- deployment lockはopen、active／unexecuted release Change Setは0。
- Bot offlineとruntime metric欠測はSTOPPED／task 0時の正常状態。30分のIDLE待機中はtaskと4 Botが
  稼働している。

## 2. Observability

- content-free structured logとEMF metricをcomponent別LogGroupへ出す。EMFは`_aws`をrootに持つ
  単一JSON eventとして出力し、Lambda structured loggerの`message`へ二重serializeしない。
- request／output／persona／URL／query／Discord IDをlogやmetric dimensionへ含めない。
- metricはruntime phase、heartbeat、Bot readiness、queue、Outbox、failure、Lambda、ECSを対象にする。
- CloudWatch dashboardはruntime／ECS、Ingress／Outbox、Bot／heartbeat、control failure、CPU／memory、
  DynamoDB throttle、alarm stateを集約する。
- critical／warning composite alarmとabnormal ECS STOPPED eventをSNSへ通知する。
- GitHub／Security通知は[[21_GitHub・Discord通知運用設計]]の補助経路で、GitHub自体を正とする。
- ADMIN statusは運用操作ではなく、allowlist済みAWS／CloudWatch read-only APIの60秒cacheから得る補助表示とする。
  source message、resource identifier、Discord identifierは収集・表示しない。cache期限前は前回値を返し、
  個別serviceの取得失敗はそのsectionだけ`unknown`または`partial`にする。
- 確認対象はECS、ECR、Inspector、S3、DynamoDB、Lambda、CloudFront、SQS、API Gateway、
  EventBridge／Scheduler、CloudFormation、SNS、SSM設定準備、Budgets／Cost Anomaly、Signer、
  AWS／OpenAI／Frankfurter collector鮮度とする。ADMINからdeploy、invoke、drift検査開始、message取得、
  secret復号、budget更新を行わない。
- ECRは現存するタグ付きimageのtag、形式、容量、push／最終pull記録だけを一覧化する。Inspectorは同じimage単位で
  severity countを色分けし、Critical／Highだけvulnerability IDと影響package／versionを展開する。
  digest、finding ARN、repository名、providerのraw descriptionは運用画面へ返さない。Critical／Highの
  raw descriptionは専用Lambdaだけが一時的に読み、`gpt-5.6-luna`のStructured Outputで100〜300文字の
  日本語概要へ変換する。raw descriptionはDynamoDB、log、APIへ保存せず、content hashと日本語概要だけを
  Statistics Tableへimmutable cacheとして保存する。未翻訳時はADMIN画面に翻訳準備中を表示する。

## 3. Routine operations

| Frequency | Operation |
|---|---|
| each PR | required CI、CodeQL、review、squash merge |
| each Release | plan evidence、Environment承認、deploy、structural smoke、cleanup |
| after Release when authorized | private Guildで最小live acceptance |
| daily | Discord security digestの結果確認 |
| weekly | core 5 stack＋Records 3 stackのdrift、dependency graph、tool version更新候補 |
| monthly／when alerted | budget、anomaly、scan finding、log volumeの確認 |
| on rotation | version付きsecret／personaを作りpointer更新、旧versionを後から失効 |

## 4. Private production configuration

新規設定、version migration、Release前のreadiness確認には、manualなGitHub／SSM更新ではなく
repositoryのguided toolを使う。最初にsecret値を取得しないmetadata checkを実行する。

```sh
uv run --frozen python tools/configure_production_inputs.py --check
```

不足設定を登録する明示工程では、入力を非表示のまま検証し、確認後にだけGitHub／SSMへ書く。

```sh
uv run --frozen python tools/configure_production_inputs.py
```

applyはlive writeでありoperatorの明示許可を必要とする。version migrationで旧設定を読む場合も、
secret／persona本文を表示、log出力、local保存しない。toolが扱う値をmanual commandへ転記しない。

ADMIN管理者のprivate inputも同じ規律で登録する。Discord user IDは専用toolのhidden inputだけで受け、
2回の入力一致を確認してから上書きを拒否し、account bindingとmetadataだけを確認する。

```sh
uv run --frozen python tools/configure_records_admin_input.py --check
# 明示的なlive write承認後だけ実行する
uv run --frozen python tools/configure_records_admin_input.py
```

Inspector翻訳用OpenAI API keyも専用toolのhidden inputを2回照合し、上書きを拒否する。
`--check`は値を復号せずSecureStringのmetadataだけを確認する。

```sh
uv run --frozen python tools/configure_records_inspector_translation.py --check
# 明示的なlive write承認後だけ実行する
uv run --frozen python tools/configure_records_inspector_translation.py
```

本文やraw identifierを手順書、shell history、
GitHub、artifactへ転記しない。

runtime prompt loaderはactive pointerが未登録の間、既存のversioned persona設定を継続する。pointerが存在する場合は
revision、manifest、5 prompt、checksumの完全一致だけを受理し、不完全または不正なら次taskをfail closedとする。
taskは開始時に1 revisionだけを読み、稼働中にhot reloadしない。

prompt変更はGitHubを経由せず、管理者が「プロンプト管理」でdraft、system差分、byte数を確認してから
`変更を反映`する。Config Lambdaは新revisionを完全保存・再検証した後だけactive pointerを切り替える。
rollbackも選択revisionの内容から新revisionを作り、過去pointerを直接再利用しない。保存後は稼働taskを
停止せず、task停止中なら`次回task待ち`、旧revisionのtask稼働中なら`自然停止待ち`、一致時は`適用済み`とする。
初回Releaseはrevisionを自動作成せず、管理者が`現在の設定を管理版として登録`する操作を別工程で行う。

## 5. Incident workflow

1. exact run、SHA、component、failure stageを固定する。
2. secret値や本文を取らず、最小logとstable error codeで直接原因を特定する。
3. stack、ECS count、lock、Change Set、durable activity、cleanupの安全状態を確認する。
4. 原因と実行済みexternal writeを記録して停止する。
5. 明示許可後、新SHAのPR／Releaseで回復する。failed runをrerunしない。

原因調査を過去PR／全runの再監査へ広げない。production stateを変えるdiagnostic、Discord／OpenAIの
試験呼出し、manual deployは独立した許可を必要とする。

## 6. Common failure boundaries

| Symptom | First evidence | Safe response |
|---|---|---|
| Interaction応答なし | Ingress Lambda category、durable acceptance | 受付有無を確認し、重複依頼を抑止 |
| STARTING長期化 | Reconciler、ECS event、image admission | terminal deadlineとdesired countを確認 |
| phase停止 | generation checkpoint、lease、Outbox plan | stale ownerを手動上書きせずrecoveryを確認 |
| Discord投稿欠落 | operation sequence、nonce、attempt、error class | history reconciliation後にFAILEDへ収束 |
| Evidence unavailable | agentic-search state、provider category | 既知failureなら空Evidence継続を確認 |
| farewell欠落 | generation／citation／Discord attempt category | best-effortとして停止継続、本文をlog取得しない |
| Release plan failure | failed step、cleanup、lock、Change Set | rerun／manual deployせず停止 |
| deploy failure | CloudFormation event、structural smoke | 元failureをcleanup resultで上書きしない |
| active prompt revision不正 | content-free validation category、active pointer有無、ECS task state | pointerを手動書換しない。現行taskを保護して原因を直し、新revisionで回復する |
| ADMIN status partial | service category、cache age、stable failure code | 本文やresource IDを取得せず、正常sectionを維持して対象serviceだけを再確認する |

## 7. Scale-down and farewell

全討論／Outbox／Status／leaseがclearになった時刻を`idle_since`とする。停止予定約5分前にfarewellを
生成・送信し、同じgenerationとIDLE状態を再確認する。挨拶は最大2 OpenAI request、最大2 Discord
sendで打ち切り、失敗しても約30分後のSTOPPINGを妨げない。

SIGTERM時は新規admissionを閉じ、active stateをcheckpointし、child taskとclientをbounded timeoutで
closeする。shutdown中にfarewellを生成／送信しない。

## 8. Recovery and drills

- DynamoDB restoreはPITRから別tableへ復元し、検証後に明示的切替計画を作る。既存tableへ上書きしない。
- dedicated ECS Exec taskはprovisionしない。Runtime障害はcontent-freeなCloudWatch log／metric、
  ECS event、durable stateを調べ、署名済みproduction imageの通常Releaseで復旧する。
- token rotationは旧／新credentialの重複期間を最小にし、4 identityを一括検証する。
- drift workflowは週次read-onlyでcore 5 stackとRecords 3 stackの計8 stackを検査し、
  自動remediationしない。
- ADMIN statusは閲覧専用とし、deploy、ECS task停止、DLQ削除、Lambda invoke、prompt pointerの手動操作を
  status画面へ追加しない。prompt本文の参照、revision作成、履歴比較、rollbackは独立したプロンプト管理画面と
  Config Lambdaだけが扱う。

PITR restoreとtoken rotationのlive drillは通常software acceptanceと分離し、実施状態を
[[20_実装・試験・検証記録]]へ要約する。
