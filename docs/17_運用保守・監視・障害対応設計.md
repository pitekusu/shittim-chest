# 運用保守・監視・障害対応設計

## 1. Normal states

外部SLAは設定しない。平常のsafe stateは次である。

- Stateful、ReleaseIdentity、Runtime、Operations、CostGovernance stackがstable。
- ECS serviceはdesired／running／pendingが0／0／0。
- Runtime controlはSTOPPED、durable activityはclear。
- deployment lockはopen、active／unexecuted release Change Setは0。
- Bot offlineとruntime metric欠測はSTOPPED／task 0時の正常状態。30分のIDLE待機中はtaskと4 Botが
  稼働している。

## 2. Observability

- content-free structured logとEMF metricをcomponent別LogGroupへ出す。
- request／output／persona／URL／query／Discord IDをlogやmetric dimensionへ含めない。
- metricはruntime phase、heartbeat、Bot readiness、queue、Outbox、failure、Lambda、ECSを対象にする。
- CloudWatch dashboardはruntime／ECS、Ingress／Outbox、Bot／heartbeat、control failure、CPU／memory、
  DynamoDB throttle、alarm stateを集約する。
- critical／warning composite alarmとabnormal ECS STOPPED eventをSNSへ通知する。
- GitHub／Security通知は[[21_GitHub・Discord通知運用設計]]の補助経路で、GitHub自体を正とする。

## 3. Routine operations

| Frequency | Operation |
|---|---|
| each PR | required CI、CodeQL、review、squash merge |
| each Release | plan evidence、Environment承認、deploy、structural smoke、cleanup |
| after Release when authorized | private Guildで最小live acceptance |
| daily | Discord security digestの結果確認 |
| weekly | 5 stack drift、dependency graph、tool version更新候補 |
| monthly／when alerted | budget、anomaly、scan finding、log volumeの確認 |
| on rotation | version付きsecret／personaを作りpointer更新、旧versionを後から失効 |

## 4. Incident workflow

1. exact run、SHA、component、failure stageを固定する。
2. secret値や本文を取らず、最小logとstable error codeで直接原因を特定する。
3. stack、ECS count、lock、Change Set、durable activity、cleanupの安全状態を確認する。
4. 原因と実行済みexternal writeを記録して停止する。
5. 明示許可後、新SHAのPR／Releaseで回復する。failed runをrerunしない。

原因調査を過去PR／全runの再監査へ広げない。production stateを変えるdiagnostic、Discord／OpenAIの
試験呼出し、manual deployは独立した許可を必要とする。

## 5. Common failure boundaries

| Symptom | First evidence | Safe response |
|---|---|---|
| Interaction応答なし | Ingress Lambda category、durable acceptance | 受付有無を確認し、重複依頼を抑止 |
| STARTING長期化 | Reconciler、ECS event、image admission | terminal deadlineとdesired countを確認 |
| phase停止 | generation checkpoint、lease、Outbox plan | stale ownerを手動上書きせずrecoveryを確認 |
| Discord投稿欠落 | operation sequence、nonce、attempt、error class | history reconciliation後にFAILEDへ収束 |
| Evidence unavailable | agentic-search state、provider category | 既知failureなら空Evidence継続を確認 |
| farewell欠落 | generation／citation／Discord attempt category | best-effortとして停止継続、本文をlog取得しない |
| Release plan failure | failed step、cleanup、lock、Change Set | rerun／manual deployせず停止 |
| deploy failure | CloudFormation event、structural smoke | 元failureをcleanup resultで上書きしない |

## 6. Scale-down and farewell

全討論／Outbox／Status／leaseがclearになった時刻を`idle_since`とする。停止予定約5分前にfarewellを
生成・送信し、同じgenerationとIDLE状態を再確認する。挨拶は最大2 OpenAI request、最大2 Discord
sendで打ち切り、失敗しても約30分後のSTOPPINGを妨げない。

SIGTERM時は新規admissionを閉じ、active stateをcheckpointし、child taskとclientをbounded timeoutで
closeする。shutdown中にfarewellを生成／送信しない。

## 7. Recovery and drills

- DynamoDB restoreはPITRから別tableへ復元し、検証後に明示的切替計画を作る。既存tableへ上書きしない。
- ECS Execはbreak-glass taskだけで、CloudWatch audit、明示承認、終了後desired 0を必要とする。
- token rotationは旧／新credentialの重複期間を最小にし、4 identityを一括検証する。
- drift workflowは週次read-onlyで5 stackを検査し、自動remediationしない。

PITR restore、ECS Exec、token rotationのlive drillは通常software acceptanceと分離し、実施状態を
[[20_実装・試験・検証記録]]へ要約する。
