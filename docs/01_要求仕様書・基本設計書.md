# 要求仕様書・基本設計書

## 1. 目的と範囲

シッテムの箱は、private Discord Guildで友人同士が判断に迷う議題を3人のAI参加者へ
相談し、異なる価値観、再検討、投票、実行可能な結論を楽しむためのBotである。

対象は1 moderator、3 participant、1 production環境である。一般公開Bot、複数tenant、
外部SLA、専門判断の代替、完全な事実調査serviceは対象外とする。

## 2. 利用者体験

1. moderator Applicationの`/shittim`へ1〜1,000文字の議題を送る。
2. BotはDiscordの応答期限内に受付結果を返し、通常text channelへ公開Statusを作る。
3. Runtimeが必要なら起動し、public threadに操作panelを作る。
4. 共通Evidenceを準備し、3人がslot順に初回意見を公開する。
5. 3人が他者意見の共通点・対立点・弱点を踏まえ、自分の人格で最終案を公開する。
6. 候補を匿名化して3人が投票し、全票確定後に投票者名、投票先、理由を公開する。
7. Pythonが得票と採点からwinnerを決め、moderatorが票数とwinnerを発表する。
8. winnerが人格固有の喜びを示し、自分の最終決定、実行案、注意点を発表する。
9. thread panelとchannel Statusを同じterminal stateへ収束させる。

固定のAI免責文は表示しない。providerのrefusal、content filter、schema検証などの安全境界は
表示方針とは独立して維持する。

## 3. 参加者と公平性

- participantは安定したgeneric slot `participant-a/b/c`で永続化する。
- display nameとpersona promptはversion付きprivate設定から読み、Gitやlogへ出さない。
- 初回意見、最終案、winner発表には3人の名簿を渡し、互いの名前と価値観を認識させる。
- 発言者は自分のpersonaだけを自分への命令として扱い、他者personaを転載しない。
- 投票では他者名簿を渡さず、候補IDと順序をattemptごとにshuffleする。
- participantは自分へ投票できない。winnerはvote count、score、安定したtie-breakから
  Pythonだけが決定する。

## 4. EvidenceとOpenAI

- すべての議題で共通Evidence Agentを1回実行する。
- Web search toolは利用可能にするが、検索するかはmodelが議題に応じて判断する。
- 検索成功時は有効なcitationまたは承認済みreal-time feedだけをEvidenceへ採用する。
- 検索不要なら`NONE / NOT_REQUESTED`、既知の検索失敗なら
  `OPTIONAL / OPTIONAL_UNAVAILABLE`として、空Evidenceで討論を続ける。
- 未知sourceや不完全な応答を事実として採用しない。未分類のprogramming errorは隠蔽しない。
- 共通Evidenceは一度永続化し、全phase／全participantが同じsnapshotを使う。
- participantごとの生成にはtoolを与えず、個別検索やEvidence差を生じさせない。

OpenAIはLuna standardを使用し、`store=false`とStructured Outputsを必須とする。OpenAIは
発言を生成するが、workflow、phase遷移、winner、retry policyを決定しない。

## 5. 状態と再開

通常phaseは次の一方向である。

```text
accepted
→ preparing_evidence
→ collecting_initial_opinions
→ discussing
→ collecting_final_proposals
→ selecting_winner
→ generating_decision
→ completed
```

非terminal phaseから`failed`または`cancelled`へ遷移できる。generation、Discord delivery、
lease、activity、status publicationをDynamoDBへ保存し、process停止後も新ownerが再開できる。

- generationはlogical output単位でclaim／checkpointし、永続outputを上書きしない。
- Discord投稿はglobal delivery sequenceを持つOutboxから1件ずつ順番に送る。
- 必須途中表示が欠落したまま`completed`にしない。
- retryは失敗attemptを改変せず、新attempt IDで作る。

## 6. Discordの表示と操作

- moderatorだけがGuild Commandを所有する。participantへcommandを登録しない。
- participantは初回意見、最終案、投票、winner発表を自分のBot identityで投稿する。
- user／role mentionを発火させず、embedを抑止し、長文はDiscord上限内へchunkする。
- 同じoperationはdeterministic nonceと履歴照合で重複を抑止する。
- Stopは新しいclaimを止め、進行中deliveryをbounded reconciliationしてterminalへ収束させる。
- RetryはFAILED attemptにだけ表示し、旧messageを削除しない。

## 7. 受付とScale-to-Zero

- Discord InteractionはAPI Gateway HTTP APIとIngress Lambdaで受ける。
- timestamp freshnessとEd25519署名を未加工bodyへ検証後、必要fieldだけを解釈する。
- 受付はDynamoDBへ永続化してから成功応答する。重複Interactionは新しいdebateを作らない。
- waiting queueは最大20件。受付後3分で非terminal警告、15分で起動不能をterminal化する。
- Reconcilerはdurable workがあればECS desired countを1、なければ0へ収束させる。
- FargateはARM64 On-Demand、最大1 task、平常`desiredCount=0`である。
- 全討論、Outbox、Status、leaseがclearになってから30分idleで停止可能とする。

停止予定約5分前には、3人からランダムに1人を選び、東京の時間帯、季節、天気、
そのpersonaが好みそうな当日ニュースを踏まえた帰宅挨拶を通常channelへbest-effortで投稿する。
OpenAI／Discordは各最大2回に限定し、挨拶失敗はscale-downを妨げない。

## 8. Data・privacy

- question、output、vote、state、delivery metadataはDynamoDBへ保存する。
- debate本文は自動期限を設けない。PITRによる復旧可能期間とは区別する。
- token、secret、Discord署名、Interaction token、persona本文をDynamoDBやlogへ保存しない。
- content-free telemetryだけをCloudWatchへ送る。question、output、URL、query、requester／Discord IDは
  含めず、opaque Debate IDとprovider response IDだけを障害相関用allowlist metadataとして許可する。
- private設定はversion付きSSM SecureStringからexact pathで読む。

## 9. Production architecture

| Component | Responsibility |
|---|---|
| API Gateway + Ingress Lambda | 署名検証、受付、短いinitial response |
| Status Publisher Lambda | 公開Statusの冪等更新 |
| Runtime Reconciler Lambda | durable stateからECS 0／1を収束 |
| Image Admission Lambda | task definitionとsigned imageを検証 |
| ECS Runtime | 4 Bot、OpenAI orchestration、Outbox delivery |
| DynamoDB | debate、queue、lease、activity、lockの正本 |
| Operations／Cost | alarm、dashboard、SNS、budget、anomaly detection |
| GitHub Actions | CI、署名、attestation、Change Set Release、drift |

CDKはStateful、ReleaseIdentity、Runtime、Operations、CostGovernanceの5 stackを所有する。
通常Production Releaseが更新するapplication stackはReleaseIdentityを除く4 stackである。

## 10. Availability and failure behavior

- task 0、Bot offline、runtime metric欠測はSTOPPED時の正常状態である。30分のIDLE待機中は
  taskと4 Botが稼働する。
- acceptance済みworkはprocess喪失、lease失効、Discord 429、OpenAI一時障害から再開可能にする。
- authentication、permission、refusal、content filter、unsafe persistent schemaは成功扱いしない。
- Evidence検索と帰宅挨拶は明示したdegraded behaviorを持ち、失敗時も安全に継続／停止する。
- automatic rollbackでdurable dataやDiscord messageを削除しない。

## 11. Quality and release

- domain／applicationは外部SDKなしで試験し、adapterはcontract testでAPI shapeを固定する。
- DynamoDB transaction、fencing、pagination、crash boundaryはDynamoDB Localとstubで検証する。
- CDK assertion／cdk-nag、docs/public-surface、dependency audit、CodeQLをrequired gateに含める。
- production imageはdigest固定し、SBOM、VEX、Grype、risk gate、署名、attestationを
  同じReleaseで検証する。cross-runの静的config digest一致は要求しない。
- Production Environment承認前にChange Setをplanし、承認後に固定順で実行する。
