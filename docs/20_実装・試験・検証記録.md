# 実装・試験・検証記録

## 1. 本書の役割

本書は、Codexとmaintainerが現在の実装到達点、重要な障害原因、最新の受入結果、未解決事項を短時間で把握するための要約である。

- 要求は[[01_要求仕様書・基本設計書]]、決定理由は[[02_議論事項・意思決定記録]]を正とする。
- interfaceとfailure処理は各詳細設計、合否条件は[[18_試験・品質保証設計]]、実装順序は[[19_実装計画・トレーサビリティ]]を正とする。
- exact command、全check、commit、run ID、artifact digest、失敗・再実行の完全な履歴はGitHub Pull Request／Actionsを正とする。本書へ逐次複製しない。
- 本書には、現行設計の判断に影響する最終結果、再発防止上必要な直接原因、最新のlive受入、未解決事項だけを残す。
- secret、本番runtime値、user content、Discord/OpenAI本文、credential、ローカル絶対pathを記録しない。
- local、CI、Production Release、live acceptanceを区別し、未実施を成功扱いしない。

## 3. 現行の検証・security境界

- required CIはquality、tests、security、package、docs、CDK、ARM64 container、Grypeを含み、CodeQL 3言語をmerge前に確認する。
- domain/application coverageは90%以上を維持する。PR `#165`の最終local suiteはDynamoDB Localを含む1,808 passed、coverage 90.22%だった。正確な継続値は各PRの最新CIを正とする。
- production／break-glassのconfig digest baselineは`security/container-risk-acceptance.json`だけを正とし、本書へ転記しない。現行schemaはv3、local acceptanceは0件である。
- image configが変わるPRはcanonical CIの同一測定で両targetを実測し、両SBOM、verified VEX、risk gateとの対応を確認してから両baselineを同じPRで更新する。
- localのproduction／break-glass full image buildは通常行わず、canonical ARM64 CIを最終判定とする。
- OpenAI、Discord、AWSのlive試験は明示承認された工程だけで行い、mock／contract成功をlive成功と扱わない。

## 4. 現行運用で保持する重要契約

1. Discord署名はraw bodyに対してJSON parse前に検証する。Interaction token、raw body、署名、質問を永続化・log出力しない。
2. Ingressはdurable acceptance前に成功を返さない。DynamoDB transaction、deployment lock、operation binding、FIFO上限を維持する。
3. RuntimeはARM64 On-Demand Fargate、通常`desiredCount=0`、最大1 taskとする。停止時はdesired/running/pending `0/0/0`、lock open、active Change Set 0を確認する。
4. OpenAI sourceと生成物はuntrusted dataである。winnerはPythonだけが決定する。
5. Outboxはnonce、fencing、content照合、有限retryを持つ。必須delivery欠落のままCOMPLETEDへ進めない。
6. Releaseはimmutable artifact、CI同一image config、signature／attestation、Change Set、Environment承認境界を維持する。失敗runをrerunしない。

## 5. 設計へ影響する主要な障害教訓

| 時期 | 直接原因 | 維持する再発防止 |
|---|---|---|
| 初回Production Release | `ecs:DescribeTaskDefinition`はresource-level ARN制限をsupportせずAccessDenied | Image Admission／Release Deployの同Actionだけを独立`Resource: "*"`。application側のtask definition／image exact検証は維持 |
| 初回image release | pytest生成bytecode、dirty workspace、異なるexporter／cache materializationでconfig digestが変化 | immutable fresh checkout、bytecode非生成・context除外、CI同一exporter／compression／cache、両target baseline同時更新 |
| PR `#175` merge後main CI | PR merge-refではbuilder final syncがcache hit、同一treeのmainではcache missとなり、両targetの差分が最終`.venv` COPY layerへ限定された。既存artifactのRECORD／SBOM内容は一致し、local同一inputのcold／warm installではmtimeだけが不一致 | RECORD／`uv_cache.json`正規化後に`.venv`の全regular file、directory、symlinkのmtimeを`SOURCE_DATE_EPOCH`へ固定し、未知file typeと正規化不能をfail closed |
| DHI更新後のPR `#178`〜`#184` | DHI更新による正当なbase layer変更と、production最終venv layerの潜在的な非決定性が同時に現れた。PRとmainは同じGit treeでもbuilder生成entryの細かなmodeが異なり得たが、transfer helperはsource modeを保存していた。コピー先へのexplicit chmodはprocess umaskだけを除去し、source mode差を残した。RECORDとSBOMのfile checksum一致はdirectory／mode一致を証明せず、aggregate canonical tree digestは差の存在だけを示してpathを特定できなかった。BuildKit recordの`containerimage.config`を最終RootFS証拠と誤認し、非対応の`BUILDKIT_MULTI_PLATFORM=1`も試したため切り分けが長期化した | production transferはdirectory `0755`、実行可能regular file `0755`、その他のregular file `0644`へ正規化し、UID/GID、mtime、content、symlink targetを固定する。source modeとprocess umaskが異なる回帰試験を維持する。DHI更新時は両targetを同じcanonical CIで測り、config digest→全RootFS diff ID→canonical tree digest→RECORD／SBOMの順に差分層を絞る。tree digestが違えばexporterやbaselineを原因と決めつけずfilesystem metadata境界として扱う。両SBOM、VEX、risk gateを確認した同一測定値だけでproduction／break-glass baselineを一括更新し、PR／main不一致は正当なDHI更新ではなく再現性failureとして停止する |
| Runtime Change Set | SecureStringをLambda Environmentのplaintext SSM dynamic referenceへ渡した | exact 2 parameterを初期化時に取得し、token-free設定だけをSnapStart snapshotへ保持。secret値は取得・記録しない |
| Runtime停止 | application importを含むhealth subprocessが3秒timeoutでfalse negative | stdlib-only health entrypoint、task固有tmpfs heartbeat、content-free exit code |
| 連続Discord実行 | discord.pyの短い`max_ratelimit_timeout`が残数ありでもpreemptive拒否 | SDK 300秒window、application側45秒timeout、Retry-After durable schedule、content-free bucket evidence |
| Ingress初期応答 | restoreとDynamoDB enqueueが1.2秒soft deadlineを超え、依頼は保存されてもephemeral応答が失敗 | SnapStart継続。PR 2でsoft deadline 2.0秒と段階別content-free timingを導入し、live 1回で微調整判断 |
| Web Evidence | `web_search_call.action.sources[].url=null`をcanonical sourceとして厳格処理し、有効citationがあっても`required_evidence_unavailable` | PR 1で`url_citation`を正本、`action.sources`を補助観測へ限定。有効citation 0件はfail closed |
| Web Evidence real-time feed | OpenAIの正規`oai-weather`応答は`type=api`、URL citationなしであり、URL-only実装がsource 0件と誤判定 | 公式3 feedだけをexact allowlistしstable source URIへ変換。未知provider／形状はfail closed、feed種別をcontent-free記録 |
| SNS email | 外部unsubscribeでCloudFormation resourceは残るがsubscription IDがDeleted | standalone subscription、認証付きconfirmation、active ARN／PendingConfirmationをread-only確認 |

## 6. 最新のProduction／live受入要約

- 2026-08-02の初回成功Releaseで4 stackはstable、ECSは`0/0/0`、deployment lockはopen、未実行Change Setは0へ収束した。以後のReleaseも同じ停止条件を必須とする。
- `/shittim`は討論完了、thread panelとchannel statusのCOMPLETED収束、連続2件のInteraction分離、ECS 0→1→0をlive確認済みである。
- Discord IngressはSnapStartと2.0秒soft deadlineを維持し、PR `#168`以降の複数live受入で「アプリケーションが応答しませんでした」を再現せず、durable受付へ成功した。Provisioned ConcurrencyやSQSは追加していない。
- Web EvidenceはPR `#167`でURL citationを正本化し、PR `#169`で公式real-time feedをexact allowlistへ追加した。以後のlive討論はEvidence経路を含めCOMPLETEDへ収束している。
- Discord討論過程表示は段階Releaseを完了した。最終live acceptanceでは、moderatorの票数・winner発表に続き、保存済みwinnerのBotがpersonaに基づく勝利コメントと最終決定を投稿した。terminal 2 operationsは固定順、各delivery attempt 1でSENTとなり、重複／ABANDONED 0、全Delivery Plan DELIVERED、Outbox／active attempt 0へ収束した。ECS停止状態はこの機能受入の対象外とした。
- Productionの正確な現在状態はrunbookのread-only確認を正とし、本書の過去snapshotだけでdeploy可否を判断しない。
