# 試験・品質保証設計

## 1. Policy

- domain／applicationを外部SDKなしでdeterministicに試験する。
- Discord、OpenAI、AWSはadapter contract testでrequest／response shapeとerror分類を固定する。
- retry、clock、random、ID、process lossをfixtureから制御し、flaky failureをrerunで隠さない。
- PR CIへproduction credential、実user content、live Discord／OpenAI writeを持ち込まない。
- local／CI、Production Release、live acceptance、destructive drillを明確に分離する。

## 2. Local and CI matrix

| Layer | Required evidence |
|---|---|
| Domain | phase edge、vote、tie-break、affection clamp／実増減、identifier、property test |
| Application | affection all-or-none／CAS、generation crash boundary、Outbox ordering、cancel／retry、activity、scale-to-zero |
| Discord contract | raw signature、3秒応答、identity、nonce、429、history reconciliation、display |
| OpenAI contract | policy、prompt、schema、agentic search、fallback、privacy telemetry |
| DynamoDB | codec、size、transaction、fencing、pagination、v7→v8 compatibility |
| Runtime process | 4 READY、recovery、health、SIGTERM、farewell、bounded close |
| CDK | strict TypeScript、Vitest assertions、cdk-nag、credentialなしsynth、IAM exactness |
| Supply chain | lock、audit、SBOM、VEX、Grype、risk policy、signature／attestation validator |
| Docs | exact 20-note mirror、Wiki link、official source、secret／ID／path scan、license |
| ADMIN／runtime prompt | loader、HMAC authorization、status、immutable publish／rollback、privacy／cache test |

PythonはRuff format／lint、ty、import-linter、full pytestをrequiredとする。DynamoDB Local runnerは
digest固定の公式containerをloopbackで起動し、production credentialを使わない。coverageは
`fail_under=90`を小数第2位まで評価し、整数丸めで90%を満たした扱いにしない。

## 3. Critical regression cases

### Ingress and state

- 未加工body以外のsignature検証、stale timestamp、unknown commandを拒否する。
- duplicate Interactionがdebateを増やさず、queue 20、warning 3分、terminal 15分を固定する。
- second requestがfirst debateのStatus／Attempt IDを変更しない。
- thread panelとchannel StatusがCOMPLETED／FAILED／CANCELLEDへ収束する。

### Generation and Evidence

- call前、response後保存前、保存後、2回目結果不明のcrashを試す。
- 同じlogical outputを永続化するのは1件だけで、個別participant Web searchは0件。
- agentic search未使用／成功／citation欠落／unknown source／429／auth／schema errorを試す。
- 既知search failureでも空Evidenceで初回意見へ進む。
- participant rosterは対象phaseだけに入り、voteとfarewellへ他者personaを渡さない。
- 親愛度は3人別request、`-100／0／+100`、上下限clamp、初期値500、固定slot順を試験する。
- 質問内の点数指定／rubric変更／persona開示を無視し、単なる反対意見を自動減点しない。
- 1件失敗時の全変更破棄、同じ評価値でのCAS retry、同じ討論の二重加算防止、
  評価後の失敗／取消でもprofileを維持することをDynamoDB Localで確認する。
- 親愛度5段階が初回意見／最終案／winner decisionにだけ入り、vote／Evidence／moderatorに入らない。

### Discord delivery

- 全phase／slot／chunk nonceが22文字で一意、sequenceどおりにarrivalする。
- first operationの429／timeout／mark-sent conflictでも後続が先行しない。
- 3票確定前のvote writeは0、確定後は実display nameと投票先を公開する。
- permission、deleted／locked thread、content conflict、deadlineでFAILEDへboundedに収束する。
- `max_ratelimit_timeout=300`とDiscord message／component上限をcontractで固定する。
- terminalは3人の適用後点と実増減を表示し、上限例の`1000点（+13）`、評価不能表示、
  Discord文字／chunk上限を検証する。

### Farewell

- idle開始25分未満はsend 0、停止予定約5分前に通常channelへ1件だけ送る。
- prompt／requestがTokyo weatherとpersonaが好む当日newsを要求し、有効citationを受理することを
  contract testで確認する。本文への実際の反映はlive表示で確認し、欠落だけでは送信を拒否しない。
- new work、generation変更、IDLE解除、SIGTERM時はsend 0。
- OpenAI／Discord各3回目へ進まず、failure後も30分scale-downが進む。
- telemetryへmessage、URL、query、persona、channel IDを含めない。

### Runtime prompt revision and ADMIN

- active pointer未登録ではlegacy設定を読む。pointerが存在する場合はmanifest、revision、5 prompt、checksumの
  完全一致だけを受理し、欠落・不正はfail closedとする。
- Config domain／adapterはLF／NFC、空白、multibyteの3,499／3,500／3,501 bytes、Crockford revision、
  初回legacy登録、publish、rollbackからの新revision、同一内容拒否、system確認文字列、base conflictを試験する。
  SSM途中失敗、pointer直前／直後、audit失敗からの回復、同一idempotency再試行、異なるrequestへのkey再利用、
  manifest欠落／checksum不一致を含め、activeへ不完全revisionを切り替えないことを確認する。
- prompt本文、raw Discord user ID、token、SSM値をlog／fixture／artifactへ含めない。
- exact Discord user IDからHMAC化したrequester keyだけがpromptを反映・rollbackできる。username、display name、
  avatarの一致は認可しない。全status／prompt APIの未認証401、認証済み一般memberのstatus取得・明示更新と
  prompt現行値・履歴・revision参照200、prompt反映・rollback403をcomponent／APIで確認する。
- Admin Statusは16 sectionの各AWS responseの欠落、pagination、部分障害、60秒cache、明示更新、
  `IDLE`（0／0／0）を試験する。API Gateway、EventBridge／Scheduler、CloudFormation、SNS、SSM、
  Budgets／Cost Anomaly、Signer、外部collectorはexact resourceまたは内部checkpointだけを参照し、
  status roleのwrite／invoke／decrypt／message receive／drift detect権限0を固定する。
  SQS message本文、SSM値、予算金額／通知先、checkpoint cursor、resource ID／ARN／bucket名／queue URL／
  Discord情報がAPI、log、fixtureの公開面へ出ないことを確認する。
- ECR／Inspectorは複数tag、untagged artifact除外、image単位aggregation、Low／Untriaged補助集計、
  Critical／Highのpackage detail、coverage欠落、aggregate不整合を試験する。Webは本番版labelと閲覧専用badgeがなく、
  Critical／High／Medium／Lowを識別可能な色で表示し、CVE、package、検出version、修正版候補をkeyboardと
  screen readerで判別できることをdesktop／mobile、light／darkで確認する。
- Inspector概要翻訳はtag付きimageのactive Critical／Highだけを対象とし、description正規化、content hash、
  1回50件／10件batch、100〜300文字、Structured Outputのkey完全一致、未翻訳表示を試験する。
  raw description、API key、finding ARNがcache、log、API、fixtureへ残らないこと、同じdescriptionを再翻訳しないこと、
  provider／SSM／DynamoDB障害がcontent-freeな安定codeで失敗することを確認する。Admin Statusは現存対象の
  cache件数、未翻訳件数、最終翻訳日時を返し、cache読取不能時は3項目を未取得としてDynamoDB cardへ表示する。
- CDKは翻訳Lambdaのreserved concurrency 1、5分timeout、毎時7分、非同期再試行0、ECR／Inspector／exact SSM／
  Statistics翻訳partitionだけのIAMを固定する。登録toolはhidden inputの一致、上書き拒否、account binding、
  metadata-only `--check`を試験する。
- Admin Config HTTPは5 routeの401／403、余分・重複query、64 KiB body、base64、Origin、CSRF、idempotency、
  404／409／503、`private, no-store`を固定する。Webは5 tab、byte counter、system差分／確認、legacy登録、
  history detailの遅延取得、rollback、409時のdraft保持と明示rebase、browser storage非保存、status障害時の
  editor継続、keyboard／320 px／light／dark／reduced motionを試験する。CDKはAdmin Config／Status Lambdaの
  reserved concurrency 2を固定する。WebはAdmin GETの429／503だけを250〜500 ms後に1回再試行し、POSTを
  自動再試行しないこと、Status取得中は手動更新を無効化することを試験する。

### Affection Records

- Archive v1／v2の読み分け、新規v2の3人分の変更前／質問評価／実増減／変更後、
  v1討論詳細の`affection=null`を固定する。
- Source Streamのprofile重複／順序逆転でもsource versionの新しい投影だけを採用し、raw Discord IDを
  Statistics、API、logへ出さない。
- 既存Archive質問者の500点seedが実profileを上書きせず、3人別の全質問者ranking、競技順位、
  score降順／表示名／opaque keyの安定sortを検証する。
- rankingは50人単位のimmutable page、400 KB上限、active pointerのCAS、pointer切替前失敗、
  1時間cursorと15分猶予中の旧generation読込、期限後cleanup、cleanup失敗からの収束を固定する。
- Admin StatusのDynamoDB sectionは`RANKING#AFFECTION / CURRENT`と`AFFECTION#SEED / CURRENT`だけを
  strong readし、正常、初回未完了、35分超のstale、future timestamp、profile／page／生成日時不一致を試験する。
  Status roleのGetItemはこの2つのpartition keyへ限定し、Webは16 service表示を維持したままDynamoDB cardへ
  profile数、初期化状態、ranking鮮度を表示する。Lambda／EventBridge／SQSは既存resourceの用途labelで親愛度との
  関係を示し、質問者key、点数、generation ID、checksumを公開しない。
- APIの認証、`limit`境界、unknown／重複query拒否、cursor改ざん／期限／limit不一致、3人格の同一offset、
  page境界をまたぐ競技順位／重複検証、`private, no-store`、private identifier／評価理由非公開を固定する。
  Webは英字subtitle `AFFECTION`、人格icon付き3 ranking、正確な点数と
  `floor(score / 100)`個を塗る10個のheart icon、
  討論詳細の変化、続きの追記／再試行、独立loading／error boundary、mobile、axeを試験する。

## 4. Container and Release gates

- production imageをcanonical ARM64条件で固定SHAからbuildする。
- production targetのconfig digest、SBOM、VEX、Grype、risk resultの対応をartifactで検証する。
- fixable High／Criticalを拒否し、unfixable residualはverified VEXまたはtarget-specific acceptanceだけを許す。
- PRで静的baselineやcross-run config digest equalityを要求しない。
- Releaseでは再buildしたproduction targetの自己整合、signature、attestation、Change Setを検証する。
- control schema更新を伴うReleaseは、uniform previousのread-only受理、lock取得と11件current化の
  1 transaction、candidate Runtime適用後のcurrent維持、未適用時のprevious一括復元、transaction
  cancellation、idempotent replay、mixed schema拒否、曖昧なstack／imageでのlock保持を試験する。
- `fault-test`はproduction risk targetに含めない。
- runtime互換層を変更するPRだけはproduction image、config digest、SBOM、VEX、risk gateを通す。
  Records-onlyのADMIN変更はFargate image buildを起動しない。CDK testはConfig／Statusのrole分離、
  Configのexact SSM／`ADMIN#PROMPT` scope、revision overwrite／delete拒否、Statusのwrite権限0、
  Stateful replacement／deletion 0を検証する。

## 5. Live acceptance

Production Releaseのstructural smoke後、明示許可したprivate Guildで次を最小1件確認する。

- `/shittim`が3秒程度で受付され、initial response failureを表示しない。
- 3人の初回意見、最終案、3票、集計、winner発表が正しいBot／順序／重複なしで出る。
- 親愛度の3人分実増減がDiscord、討論詳細、質問者別rankingで一致し、次回応答の態度に反映される。
- channel Statusとthread panelがterminalへ収束する。
- 時間非依存の議題ではsearch skip、現在情報の議題ではshared searchをcontent-free telemetryで確認する。
- idle約25分でfarewell 1件、約30分でECS 0／0／0へ戻る。

liveで全winner組合せ、multi-chunk、障害注入を繰り返さず、local／contract testへ委ねる。

ADMIN Releaseのstructural smokeはSessionの`isAdmin`表示、匿名ADMIN APIの401、管理者入力metadataの存在、
Lambda alias／route／access logのprivacyを確認する。prompt管理Releaseでは匿名prompts APIの401／no-storeも
固定する。一般memberのstatus表示、prompt閲覧専用表示、反映・復元操作の非表示とAPI 403、管理者の編集操作は
browser受入で確認し、初回active revision作成はRelease後の独立した管理操作として扱う。

## 6. Operational drills

token rotationとPITR restoreはproductionへ影響し得るため、1.0 software DoDの
required testに含めない。operator承認、rollback、証拠保存を個別に計画し、未実施を成功扱いしない。
